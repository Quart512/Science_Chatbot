# README_12 — CI/프론트엔드 정비 · 아키텍처 개편 · 논문 요약기(②a) 완성

> 이 문서는 11주차 이후(07-23~07-28) 작업 회고다. **날짜별로 무엇을 했는지는 [RoadMap.md](RoadMap.md)가 단일 진실 소스**이므로 여기서 중복하지 않는다 — 이 문서는 "왜 그렇게 했는지"와 실제로 겪은 문제·교훈만 남긴다.

## 1. 배포 전 테스트 게이트 (CI)

`deploy.yml`을 `test`/`deploy` job으로 분리해 테스트 실패 시 배포 자체가 시작 안 되게 했다. 실제로 게이트 역할을 한 사례가 있다 — `State`에 필드를 추가하면서 관련 테스트 갱신을 깜빡했는데, 로컬 확인 없이 push했다가 CI의 `test` job에서 바로 잡혔고 `deploy` job은 시작조차 안 됐다.

07-28에 한 번 더 손봤다: 이 test job이 push(main)에만 붙어 있어 **PR 단계에서는 테스트 결과가 안 보이고 merge 이후(배포 직전)에야 실패가 드러나는 구조**였다. `test.yml`을 재사용 워크플로우(`workflow_call` + `pull_request` 트리거)로 분리해 PR에도 직접 붙이고, `deploy.yml`의 test job은 이제 그걸 `uses:`로 호출만 한다(pytest 스텝은 한 곳에만 유지).

## 2. 프론트엔드(Streamlit) + 컨테이너 분리

`/docs`(Swagger UI) 대신 쓸 최소 채팅 UI를 Streamlit으로 붙였다(`frontend/`, 완전히 분리된 서브프로젝트·별도 이미지) — 백엔드 이미지를 8.77GB→2.04GB로 줄여둔 작업이 Streamlit의 무거운 의존성 트리로 무효화되지 않게 하려고. `docker-compose.yml`에 `profiles: ["frontend"]`로 선택 설치되게 했고, 처음엔 "필요할 때 수동 설치"로 가려다가 매번 손으로 옮기는 게 번거로워서 **CI가 백엔드+프론트를 항상 같이 빌드·배포**하도록 바꿨다(이미지 빌드+push, `docker-compose.yml` 자동 scp, `--profile frontend`로 배포). `DEPLOY.md`도 이 흐름에 맞춰 갱신했다. nginx 리버스 프록시 도입은 **보류** — 도메인·공개 서비스화 전까지는 얻는 게 없다는 판단(재고 조건은 RoadMap에 기록).

## 3. verify가 단기기억(대화 이력)을 못 보던 버그

**증상**: "내 이름은 원정재야" → 정상 응답. 이어서 "내 이름이 뭐라고?"라고 물으면 generate는 이력을 보고 맞게 답하는데도 verify가 매번 "근거 없이 지어냈다"며 반려 → limit까지 재시도만 반복하다 결국 "알 수 없습니다"로 답이 뒤집힘.

**원인**: `generate()`는 `state.messages`(대화 이력)를 모델에 넘기는데, `verify()`는 애초부터 `[system, 질문+답변]` 두 개만 넘기고 있었다 — **대화 이력 자체를 아예 안 보내고 있었다.** 모델이 멍청해서가 아니라 단기기억을 안 준 게 원인.

**수정**: `verify()`의 메시지 목록에 `state.messages`를 그대로 이어붙이고, 시스템 프롬프트에 "대화 이력의 정보도 근거로 인정하라"는 지침을 추가했다. 겸사겸사 — 이 상태로는 재시도·tool 메시지가 다음 턴까지 계속 누적되므로, `turn_start_len`(턴 시작 시점의 `len(messages)`)을 State에 추가해 `final_answer`가 이번 턴 몫만 `RemoveMessage`로 정리하고 질문+최종답변 한 쌍만 남기게 했다.

**해프닝**: 수정 후에도 컨테이너가 옛날처럼 동작해 "로직이 진짜 안 고쳐졌나" 헷갈렸는데, `docker exec`로 컨테이너 안 소스를 직접 까보니 재빌드가 실제로 안 된 상태였다 — 로그·추측만으로 판단하지 말고 컨테이너 안을 직접 봐야 "이미지 문제 vs 로직 문제"가 구분된다는 교훈.

## 4. 아키텍처 개편 — 단일 슈퍼바이저 챗봇 → 표면/능력/데이터 3층

멀티 에이전트 확장 착수 직전 전체 설계를 재검토했다. "오케스트레이터가 여러 전문 에이전트를 라우팅하는 단일 챗봇"도, "서비스별 챗봇 분리"도 둘 다 아니었다 — 진짜 문제는 **모든 기능을 대화형 챗봇으로 만들려 한 것 자체**였다.

결론: 기능을 성격별로 3층에 놓는다 — **표면**(사용자가 만나는 화면, 작업 성격에 맞는 UI 형태: 메인 챗/연구 워크플로우/라이브러리/피드), **능력**(호출당하는 서브그래프·함수, 챗봇 아님: 물리 QA·논문 요약기·문서 작성기 등), **데이터 서비스**(CRUD+검색: 관심사 저장소·논문 VDB·카탈로그 등). 핵심 통찰: 논문 분석기는 챗봇이 아니라 여러 곳이 재사용하는 **허브 능력**, 추천은 챗봇이 아니라 **cron 파이프라인**, 문서 작성기는 **템플릿만 갈아끼우는 공유 서브그래프**.

이 개편이 실행 순서에 미친 수정은 상세 근거와 함께 RoadMap §설계 노트에 있다 — 요지만: 서브그래프는 래퍼 함수 노드로 포장(컴파일된 그래프 직접 삽입 시 `messages` reducer가 부모와 섞임), checkpointer·턴 경계는 부모(오케스트레이터) 소속, 스트리밍은 워크플로우 구축 **전에** 도입, SqliteSaver는 HITL **앞으로** 당김, comment(사용자용)/trace(디버그) 채널 분리.

## 5. 6-1·6-2 실행 — orchestrator 분리 · effort 프로필 · 스트리밍

§4의 방식대로 `graph.py`(물리 QA, checkpointer 없음)를 `orchestrator.py`(단기기억·checkpointer 소유, 래퍼 함수 노드로 능력 호출)로 분리했다. `reset_turn` 노드는 옮길 필요조차 없이 통째로 삭제됐다 — orchestrator가 매 턴 능력을 fresh invoke하므로 Pydantic 기본값이 이미 초기화 역할을 대신한다.

top_k/limit은 여전히 "능력 내부 다이얼"로 부모 State에 안 넣되, Claude의 reasoning effort와 같은 패턴으로 `low/medium/high` 선택지만 사용자에게 노출(`EFFORT_PROFILES` 매핑은 `graph.py` 안에 캡슐화).

스트리밍은 당초 계획한 `stream_mode="updates"`가 래퍼 함수 노드 구조상 안 맞았다(부모 그래프엔 노드가 하나뿐이라 능력 내부 진행상황이 안 보임) — 대신 능력을 `stream(stream_mode="values")`로 순회하며 `get_stream_writer()`로 부모의 `stream_mode="custom"`에 흘려보내는 방식으로 조정. 이 과정에서 comment 필드가 "내부 디버그 로그"와 "사용자용 코멘트" 두 역할을 겸하고 있던 게 드러나 `trace`(디버그) / `comment`(verify의 구조화 출력만) 로 분리했다.

## 6. arxiv API 이슈 해결 (6-3 선행)

DDG `site:arxiv.org` 우회는 스니펫만 줄 뿐 논문 분석기가 필요로 하는 구조화된 서지정보(제목·저자·연도·arxiv id)를 못 줘서, `export.arxiv.org` 공식 API를 표준 라이브러리(`xml`)+`requests`로 직접 호출하는 `arxiv_api.py`를 만들었다. 실행 중 겪은 `ReadTimeout`을 `curl -v` 대조 테스트로 "코드 문제가 아니라 arxiv 자체 rate limit(429/503)"임을 진단 → 3초 스로틀링 + `Retry-After` 존중 재시도로 해결. 파싱 로직(`_parse_atom_response`)을 네트워크 호출과 분리해 실제 API 없이 pytest 검증 가능하게 만들었다(§3의 "컨테이너 직접 확인"과 같은 계열 교훈 — 로그·추측 대신 직접 대조해서 원인을 좁힌 사례).

## 7. tool 라운드 예산 낭비 버그

실전에서 `search_arxiv` 연속 2회 실패로 서킷 브레이커가 켜진 뒤, LLM이 그 사실을 모르고 재요청 → `[사용 불가]`로 거부됐는데 **이 거부까지 `tool_rounds`를 소모**해버려서, 정작 fallback tool(`duckduckgo_search`)이 한도 초과로 시도조차 못 해본 채 끝난 사례를 SSE 트레이스로 재구성해 발견했다. `run_tools()`에 `attempted` 플래그를 추가해 실행을 시도조차 안 한 조기 거부는 라운드로 안 세도록 수정 — 전역 라운드 캡 자체는 유지(tool별 서킷 브레이커와는 막는 대상이 다름: 여러 tool을 번갈아 실패하는 라운드-로빈 무한루프 방지).

## 8. 논문 요약기(②a) 전문 처리 완성 (6-3)

착수 전 재검토로 "abstract 트리아지 → 전문 요약" 단일 파이프라인이 성립하지 않음을 확인 — 유료 저널은 트리아지 통과해도 전문을 못 읽고, 보유 논문은 이미 선별이 끝나 트리아지가 불필요. **논문 요약기(②a, 보유 논문 전문·lazy)/스크리닝(②b, abstract+지표)/검색 어댑터** 3분할로 재설계하고, 6-3 범위를 ②a로 좁혔다.

구현은 유틸리티 → 오케스트레이션 순으로 쌓았다: `pdf_parse.py`(PyMuPDF 어댑터, AGPL 고지 후 격리)·`paper_sections.py`(헤더 기반 섹션 분할+병합, References `is_references` 태깅, 임베딩 전용 청킹 `split_for_embedding`)·`paper_id.py`(DOI>arXiv>파일해시 우선순위 정규화, 재등록 멱등성)·`paper_extraction.py`(품질 판정이 아니라 구조화 추출 — 핵심 주장/근거/저자가 밝힌 한계/미해결/코드공개)·`models.py`(모델별 `CONTEXT_BUDGET_CHARS` + `check_context_budget`, `ContextBudgetExceeded`는 의도적으로 fallback 예외 목록 밖). 이 조각들을 `paper_ingest.py`의 `register_paper()`(등록 시 인코딩만)·`get_paper_summary()`(조회 시 lazy 추출+캐시)로 통합했다.

과정에서 실제 리뷰(효율이 아니라 안전 문제라는 지적)를 반영해 `paper_id`·preprint 여부처럼 이미 알거나 계산 가능한 값은 LLM 스키마에서 빼고, `from_section`은 index 기반 `from_chunk`(RAG식 재조회)로 바꿨다. 컨텍스트 예산 초과 시엔 재귀 분할(map-reduce) 대신 **단순 경로 + 정직한 실패**를 택했다 — 실제로 걸리는 사례를 만나면 그때 분할을 추가한다는 원칙.

`retrieval.py`에 물리 QA용 `feynman`과 분리된 `papers_vectorstore`(같은 임베딩 모델 공유, `doc_type: fulltext_chunk/summary`로 구분)를 신설하고, `graph.py`의 `retrieve()`가 이 컬렉션도 검색해 QA에 논문 참고를 추가 LLM 호출 없이 붙이게 했다(빈 컬렉션이면 그냥 빈 결과 — 기존 eval 점수에 영향 없음). 실제 14페이지 논문으로 등록(122청크)+요약 생성까지 스모크 테스트 확인.

마지막으로 "요약 부재 시 전문 청크로 답하고 요약 생성은 백그라운드로" 요구를 채웠다. 전반부는 사실 별도 코드가 필요 없었다 — 요약 문서가 없으면 유사도 검색이 애초에 `fulltext_chunk`만 돌려주기 때문. 후반부(`paper_ingest.py`의 `ensure_summary_in_background()`)는 daemon thread로 `get_paper_summary()`를 실행하고 즉시 반환해 이번 턴을 막지 않는다 — 완료를 실시간으로 통지하는 채널은 안 만들었다(다음 조회 때 캐시로 잡히는 것 자체가 결과). 같은 논문이 멀티턴 대화에서 짧은 간격으로 여러 번 걸리는 경우를 대비해 모듈 전역 in-flight 집합으로 중복 생성만 막았다. 실제 스레드 기동을 `_spawn_background()` 한 줄짜리 함수로 분리해, 테스트에서는 이 함수만 동기 실행으로 갈아끼워 진짜 스레드·진짜 LLM 없이 판단 로직(캐시 확인·중복 방지)을 검증했다.

카탈로그(SQLite, 상태 관리)는 의도적으로 이번 범위 밖에 뒀다 — 지금은 Chroma 메타데이터가 등록 여부의 유일한 기록이고, 상태(recommended/owned/dismissed) 관리는 6-6에서.

## 회고

이 구간에서 반복된 교훈 하나: **개별 함수 단위 pytest로는 못 잡는 버그가 있다.** verify 단기기억 누락도, tool 라운드 예산 소모도 둘 다 각 함수만 보면 정상이었고 실제 멀티턴 대화·여러 라운드에 걸친 실전 시나리오에서야 "정보가 이 노드까지 전달되는가", "거부도 라운드를 먹는다" 같은 노드 간 상호작용이 드러났다. 톨게이트 테스트가 커버하는 범위와 실제로 써봐야 드러나는 범위는 다르다. "재빌드 안 됐는데 로직 버그로 오인할 뻔한 것"도 같은 계열 — 로그·추측 대신 직접 까봐야 확실해진다.
