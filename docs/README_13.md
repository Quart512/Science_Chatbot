## 1. `register_paper()` 카탈로그 연동 (08-09 마무리)

`paper/paper_ingest.py`의 `register_paper()`가 정상 등록(text_extractable) 시 `paper_catalog.mark_owned()`를 호출하도록 연결했다. 추천 검색(③)이 `upsert_recommended()`로 이미 심어둔 `recommended` 행이 있으면 `owned`로 전환하고, 없으면(추천 없이 바로 등록한 논문) 새로 만든다. `title`/`authors`/`year`는 등록 과정에서 이미 계산해둔 `bib_meta`(화이트리스트로 거른 서지정보)를 재사용 — 새로 뽑지 않는다.

**스캔본은 카탈로그도 안 건드린다** — VDB에 아무것도 저장하지 않는 것과 대칭. 카탈로그 쓰기 실패는 arxiv 자동조회(네트워크, best-effort)와 달리 삼키지 않고 그대로 전파한다 — "카탈로그에 반영됨"이 이제 이 함수 계약의 일부이기 때문이다.

**cross-id 매칭은 의도적으로 미뤘다**: 추천 시점엔 arxiv_id만 있어 `paper_id`가 `arxiv:XXXX`로 계산됐는데, 등록 시점에 사용자가 (arxiv가 안 준) DOI를 새로 넘기면 `normalize_paper_id()`가 DOI 우선이라 `paper_id`가 바뀌어 기존 `recommended` 행을 못 찾고 새 행이 생기는 경우가 있다. 라이브러리 UI가 아직 없어 이런 입력이 실제로 어떻게 들어올지 모르는 채로 매칭 로직을 미리 만들 근거가 없었다 — 실제로 걸리면 그때 doi/arxiv_id 컬럼으로 보완한다.

## 2. 08-11 라이브러리 표면 1차

### 2.1 순서 재검토

원래 로드맵 순서는 08-10(메인 챗 라우터) → 08-11(라이브러리 표면)이었다. 08-10을 먼저 설계하다가 막혔다 — 라우터가 라우팅할 대상 중 "문서 작성기"(⑦)는 아직 없고, "추천 조회"도 막상 보니 `paper_catalog`에 `interest_id` 연결이 없어 "이 관심사에 추천된 논문"처럼 특정해서 못 물어본다(전역 목록만 가능). 게다가 07-24 아키텍처 개편 이후 "추천 조회"는 원래 메인 챗이 아니라 **라이브러리 표면**(전용 UI 버튼)이 맡는 게 자연스럽다 — 사용자 지적으로 순서를 뒤집어 08-11을 먼저 하기로 했다.

### 2.2 프론트 스택 — Streamlit 유지

로드맵은 "표면 4개엔 Streamlit 한계, React 등 전환 검토"를 08-11과 겸행하기로 했었다. 이번엔 Streamlit을 유지하기로 결정했다 — 백엔드 엔드포인트는 스택과 무관하고, `st.navigation()`이 멀티페이지 전환에 저비용이라 지금 화면부터 만들고, React 전환이 필요해지면(화면이 더 늘거나 한계에 부딪히면) 백엔드는 그대로 두고 화면만 새로 짜면 된다.

### 2.3 멀티페이지 전환

`frontend/app.py`를 `st.navigation()`+`st.Page()`로 네비게이션만 담당하게 바꾸고, 기존 챗 화면은 `frontend/views/chat.py`로 그대로 옮겼다(기능 변경 없음). `pages/` 디렉터리 자동 인식 방식(구 Streamlit 관례) 대신 `st.navigation()`을 쓴 이유: 파일명 슬러그로 페이지 이름이 정해지는 관례보다 그룹(메인/라이브러리)·아이콘·기본 페이지를 명시적으로 통제할 수 있어서다.

### 2.4 논문 탭 (`frontend/views/papers.py`)

- **`POST /papers`(신규)**: `register_paper()`가 지금까지 `paper/paper_ingest.py`의 `__main__` 스모크 테스트로만 호출되던 걸 API로 처음 노출했다. `register_paper()`가 `pdf_path`(디스크 경로)를 받는 시그니처라, 업로드 바이트를 임시 파일에 한 번 써서 그 경로를 넘긴다(`register_paper()` 자체를 bytes 인자로 바꾸는 건 이 엔드포인트 하나만을 위한 리팩터링이라 범위 밖으로 뒀다). `fitz.FileDataError`(PyMuPDF가 유효한 PDF가 아니라고 판단할 때)는 사용자 입력 검증 경계에서 나는 에러라 500이 아니라 400으로 변환한다 — 지금까지 `register_paper()`의 유일한 호출자(CLI 스모크 테스트)는 항상 진짜 PDF를 줬으니 이 실패 모드를 신경 쓸 필요가 없었지만, API로 노출되는 순간 신뢰 못 할 입력이 된다.
- **`GET /papers`(신규)**: 카탈로그 전역 조회(`status` 쿼리 파라미터로 필터). 관심사별 필터는 `interest_paper` 조인 테이블이 없어 아직 불가.
- 등록 폼 제출 후 `title_check.status == "different_paper"`면 경고 표시, 카탈로그 목록은 고정 높이(300px) 테이블로 내부 스크롤(안 그러면 논문이 많아질수록 페이지가 계속 늘어남).

### 2.5 관심사 탭 (`frontend/views/interests.py`) — 1차

- **`GET /interests`(신규)**: 지금까지 생성(`POST`)만 API로 열려 있고 조회가 없었다.
- **`DELETE /interests/{id}`(신규)**: `interests.py`에 `delete_interest()` 추가. `interest_paper` 조인 테이블이 아직 없어 이 관심사가 추천한 카탈로그 행을 같이 지울지는 그 테이블이 생길 때 정하기로 하고, 지금은 `interests` 테이블 행 하나만 지운다.
- **수동 생성 폼**: 관심사를 만드는 원래 경로는 챗의 제안 흐름(`suggest_interest_node`가 초안을 만들면 "관심사 등록" 버튼으로 저장)이지만 그 버튼이 아직 프론트에 안 붙어 있어, 관리 UI답게 직접 만드는 경로도 같이 뒀다.
- 카드별 **수정** 폼은 기존 `POST /interests`의 `update_existing_id`를 그대로 재사용.

## 3. 관심사 탭 개선 3종 (같은 세션 내 추가 요청)

### 3.1 추천 검색 페이지네이션 — "추가 검색"

기존 "지금 검색" 버튼은 매번 `start=0`으로 같은 상위 결과만 돌려줬다. `arxiv_search()`가 `start`를 0으로 고정해뒀던 걸 열어 `paper_search.search_papers()` → `paper_recommend.recommend_for_interest()` → `POST /interests/{id}/search?start=`까지 관통시켰다. 프론트는 세션에 지금까지 받은 개수(offset)를 들고 있다가 다음 페이지 요청에 그대로 넘긴다.

### 3.2 관심사 수정 시 자동 재검색

사용자 지적: "관심사가 수정되면 수정된 내용에 따라 다시 검색해야 하는데, 기존에 검색했던 논문을 활용할 수 없을까?" — 수정이 큰 변화가 아닐 수도 있으니 기존 후보를 버리지 말자는 취지.

`paper_recommend.refresh_for_interest(interest_id, existing_candidates)`를 새로 만들었다:
1. 프론트가 세션에 쌓아둔 기존 후보(이미 한 번 스크리닝된 것)를 **수정된 관심사 기준으로 재스크리닝**해서 관련 있는 것만 남긴다(관련 없어진 건 버림).
2. 동시에 `recommend_for_interest()`로 **새 페이지 하나(`start=0`)를 정상 검색**한다(카탈로그 upsert도 그 경로가 기존과 똑같이 처리).
3. 겹치는 `paper_id`는 새 쪽에서 제거(중복 표시 방지), 합쳐서 관련도로 재정렬.

**구현상 트릭**: 프론트가 들고 있는 기존 후보 dict엔 `journal_ref` 원본이 없다(`peer_reviewed` bool로만 축약돼 전달됨). `screen_candidate()`는 `candidate.get("journal_ref")`로 `peer_reviewed`를 재계산하므로, 역산해서 `peer_reviewed=True`였으면 아무 비어있지 않은 문자열을 `journal_ref`에 채워 넣는다 — `bool(journal_ref)`가 다시 `True`로 복원되기만 하면 되고, 이건 재판정이 아니라 값을 보존하는 것뿐이다.

**재스크리닝으로 살아남은 기존 후보는 카탈로그에 재upsert하지 않는다** — 프론트가 들고 있던 후보엔 애초에 doi/arxiv_id가 없어(첫 검색 응답에도 안 실었음) 정확한 메타데이터로 넣을 수 없고, "카탈로그에 남기는 것"과 "화면에 보여주는 것"을 분리하는 `paper_recommend.py`의 기존 원칙과도 맞다.

**보류한 것**: 애초엔 "기존 것과 별개로 한 번 더 신선한 재검색"도 하자는 이야기가 있었지만, 실제로는 "재검색"이라는 별도 메커니즘을 만드는 대신 그냥 기존 검색/추가 검색 버튼을 다시 누르면 되는 걸로 정리됐다 — 관심사가 수정되면 그다음 검색 클릭이 자연히 새 기준을 반영하기 때문이다.

### 3.3 검색/추가 검색 버튼 통합

두 버튼(지금 검색 / 추가 검색)이 나란히 있는 대신, 하나의 버튼이 상태에 따라 라벨과 동작을 바꾼다 — 카드에 쌓인 결과가 없으면 "지금 검색"(`start=0`), 있으면 "추가 검색"(`start=offset`)으로. 버튼 클릭 직후 `st.rerun()`을 명시적으로 호출하는데, 이는 Streamlit이 클릭 시 이미 한 번 스크립트를 재실행한 상태라 세션 상태 갱신 후 라벨이 즉시 "추가 검색"으로 바뀌려면 한 번 더 재실행이 필요하기 때문이다(안 그러면 다음 상호작용 전까지 라벨이 낡은 채로 남는다).

### 3.4 표시 개선

- "관련 있음" O/X 컬럼을 없애고, 이미 관련도순으로 정렬돼 오는 순서를 그대로 신뢰해 순위 번호로 대체했다.
- 결과 테이블에 고정 높이(300px)를 줘서 내부 스크롤로 바꿨다(논문 탭의 카탈로그 테이블도 동일 처리).

## 4. `invoke_with_fallback` 예외 화이트리스트 갭 2건

라이브러리 UI 실사용(관심사 검색) 중 API 쿼터/크레딧 소진이 겹쳐 발견했다.

**(1) `google.genai.errors.ServerError`**: `langchain_google_genai`가 내부적으로 `google-genai` SDK로 갈아탄 뒤로, gemini 과부하(503)가 `ChatGoogleGenerativeAIError`로 안 감싸이고 그 SDK의 원본 예외 그대로 올라온다. 잡지 않으면 fallback을 못 타고 `RuntimeError`도 아니라서 호출부(`screen_candidate` 등)의 "실패한 후보만 건너뛴다" 처리도 못 받고 그대로 500까지 샜다(실제 재현). `ClientError`(4xx)/`ServerError`(5xx) 둘 다의 공통 부모(`google.genai.errors.APIError`)를 잡아 전부 fallback 대상으로 포함시켰다.

**(2) `anthropic.BadRequestError`**: anthropic 계정 크레딧 부족도 400(`BadRequestError`)으로 온다. 기존 화이트리스트의 `openai.BadRequestError`와 이름은 같지만 서로 다른 SDK의 별개 클래스라 하나를 잡는다고 다른 하나까지 잡히지 않는다 — 실제로 gemini 쿼터 소진 → claude로 fallback → claude도 크레딧 부족으로 실패하는 이중 장애를 겪으며 발견했다.

`models.py`의 예외 화이트리스트에 두 타입 다 추가하고, 회귀 테스트 2개(각각 실제 예외 인스턴스를 구성해 fallback이 정상적으로 다음 모델로 넘어가는지 확인) 추가.

## 5. Gemini 모델 교체

사용자 제보: `gemini-3.5-flash-lite`가 `gemini-2.5-flash`보다 무료 티어 일일 요청 한도가 훨씬 높다. 구글 공식 모델 문서(`ai.google.dev/gemini-api/docs/models`)와 AI Studio 요금 한도 페이지로 모델 ID(`gemini-3.5-flash-lite`, 실존 확인)와 컨텍스트 윈도우(1M 토큰급, 기존과 동급)를 확인한 뒤 `model_map["gemini"]`를 교체했다. 컨텍스트 윈도우가 동급이라 `CONTEXT_BUDGET_CHARS["gemini"]`는 안전 마진을 더 늘려 200만 자로 상향했다(기존 80만 자 — 논문 전문이 걸릴 여지를 더 줄이려는 목적, flash-lite도 1M 토큰급이라 여유 있음).

`evaluation/evaluate.py`가 별도로 `gemini-2.5-flash`를 하드코딩해 쓰는 곳(judge 등)은 재현성 목적의 독립적인 선택이라 이번 교체 범위에서 제외했다.

## 7. 실험도구 DB(⑤) · 참고문헌 추천기 · 연구 워크플로우(⑥) — 백엔드 완성

08-02~08-03 구간. 로드맵의 "실험도구 DB(⑤) + 연구 워크플로우(⑥)" 한 줄짜리 항목을 실제로 착수하면서, 계획에 적혀 있던 것과 다르게 간 판단이 여럿 나왔다. 이 절은 **그 어긋난 지점들**을 남긴다 — 무엇을 만들었는지는 RoadMap 완료 표에 있다.

### 7.1 계획을 바꾼 지점 4개

**(1) ⑤의 RDB 근거가 실제로는 안 쓰였다.** "VDB vs RDB" 설계 노트가 RDB를 고른 근거는 "측정 범위가 X 이상인 장비 있나?" 같은 **SQL 범위 조회**였다. 그런데 막상 만들 때는 스펙 세부를 전부 `detail` 자유 텍스트로 몰고, 연구 워크플로우가 장비를 찾을 땐 **목록을 통째로 프롬프트에 넣어 LLM이 읽게** 했다. 결과적으로 RDB를 고른 원래 근거는 한 번도 안 쓰인 셈인데, 그렇다고 결정이 틀렸던 건 아니다 — 같은 설계 노트의 **다른** 근거("목록이 짧으니 프롬프트에 넣으면 된다")가 대신 성립했기 때문이다. 진짜 숫자 범위 조회가 필요해지면 그때 `detail`에서 컬럼을 분리한다.

**(2) 실험 설계의 "Plan-and-Execute"를 안 썼다.** README가 이 단계의 핵심 기법으로 Plan-and-Execute(계획자가 단계를 짜고 실행자가 tool을 섞어 수행, 필요시 재계획)를 적어뒀지만 분리하지 않았다. 근거: Plan-and-Execute가 막으려는 건 "설계 없이 바로 행동"인데, **이 단계의 산출물 자체가 설계 문서라 '실행'이 따로 없다** — 행동은 다음 단계에서, 그것도 사람이 실험실에서 한다. 패턴 이름이 로드맵에 적혀 있다는 이유로 구조를 맞추는 건 거꾸로다.

**(3) 안전 가드레일에 `interrupt_before`를 안 썼다.** 이건 설계 노트가 오래 "진짜 HITL이 필요한 유이한 지점"으로 지목해온 자리였다(다른 하나인 문서 작성기는 07-31에 이미 폐기). 재검토 결론은 여기도 불필요 — **이 그래프는 물리적 행동을 하지 않고**(실험은 사람이 직접 한다) 단계 전환 자체가 이미 사람 트리거라 자연스러운 승인 지점이 있다. 막을 실행이 없는데 실행을 막는 장치를 다는 셈이었다. 그래서 **이 프로젝트에 실행을 막는 진짜 interrupt가 필요한 지점은 결국 하나도 없었다**는 게 최종 결론이다.

대신 장비에 `precautions` 필드를 두고(별도 `safety_rules.py`를 만들지 않은 건 사용자 제안 — 주의사항은 장비 자체에 속하는 정보다), 설계에 그 장비 이름이 나오면 주의사항을 `comment` 맨 앞에 붙이는 **LLM 없는 이름 매칭** 노드로 처리했다. 하는 일이 "안전한지 판단"이 아니라 "사람이 미리 등록해둔 경고를 놓치지 않게 보여주기"로 바뀐 것이다 — 판정 대신 추출/신호 원칙과 같은 결.

**(4) 단계 전환 방식을 갈아엎었다(가장 큰 것).** 아래 §7.2.

### 7.2 단계 전환 — 글루 함수에서 START 라우팅으로

처음엔 가설→참고문헌→설계→…를 전부 자동으로 잇는 단일 체인이었다. 문제는 참고문헌 노드가 "선행 연구가 있는지 확인하고 재생성할지 판단하라"는 안내를 남겨도 **그래프가 다음 단계까지 그냥 달려버려 검토할 틈이 없다**는 것이었다. 단계 사이 전환은 전부 사람이 트리거해야 한다.

1차 구현은 글루 함수였다: `aget_state`로 상태를 읽고 → 파이썬 함수를 직접 부르고 → `aupdate_state`로 쓰기. 여기에 사용자가 **"그냥 START에서 라우팅하면 안 되냐"**고 물었고, 별도 토이 그래프로 실제 동작을 확인한 뒤 그쪽으로 교체했다. `WorkflowState.stage`를 `route_by_stage()`가 보고 START에서 분기하며, 각 단계는 `[생성 노드] → [참고문헌 노드] → END`다.

확인한 것 두 가지: (a) `ainvoke({"stage": "design", ...새 입력}, config)` **한 번**이면 stage 갱신과 새 입력(예: 실험 결과)이 같은 호출 안에서 함께 반영된다 — 별도 `aupdate_state`가 필요 없다. (b) 그 노드는 체크포인트에 이미 있는 이전 단계 값을 그대로 본다.

바꾸고 나서 드러난 이점이 원래 기대보다 컸다:
- **1단계만 특별 취급하던 비일관성이 사라졌다.** 글루 방식에선 가설만 그래프로 돌고 나머지는 파이썬 함수 직접 호출이라 스트리밍·트레이싱이 단계마다 달랐다.
- **"재설계 필요" 판정에 되돌아가는 엣지가 필요 없다.** 사람이 stage를 "design"으로 되돌리기만 하면 된다.
- 단계가 늘어도 새 글루 함수 없이 라우팅 분기 + 엣지만 추가하면 된다.

### 7.3 `screen_candidate`를 관심사 dict에서 문자열로 좁히기

참고문헌 추천기는 ③ 추천 검색과 검색·스크리닝 부품을 공유해야 하는데, 입력 성격이 다르다 — ③은 "등록된 넓은 주제 하나", 추천기는 "문장 하나"마다 호출된다. `screen_candidate(candidate, interest: dict)` 그대로 쓰려면 **가짜 interest 객체를 만들어 넘겨야 했다.**

그래서 두 번째 인자를 `topic: str` 자유 텍스트로 좁히고, 관심사 4필드를 텍스트로 조립하는 책임은 호출자(`paper_recommend._interest_topic_text()`)로 밀었다. 이 함수는 이제 텍스트의 출처를 몰라도 된다. 인터페이스를 **넓히는** 대신 **좁혀서** 재사용성을 얻은 사례다 — 시스템 프롬프트도 "'찾는 것'이 적혀 있다면 거기 초점을 맞추되, 그런 구분이 없으면 이 기준은 무시하라"로 양쪽을 다 받게 고쳤다.

### 7.4 리뷰 8건 — 테스트가 원리적으로 못 잡던 것들

구현 직후(다음 기능 얹기 전) 전체를 훑어 8건을 발견·수정했다. 상세는 RoadMap 08-03 행에 있고, 여기엔 **교훈이 남는 것 세 개**만 적는다.

**(A) `CREATE TABLE IF NOT EXISTS`는 컬럼을 추가하지 않는다.** `precautions`를 나중에 스키마에 넣었는데, 이 문장은 테이블이 이미 있으면 아무것도 안 한다. 3필드 시절 테이블이 남아있는 환경(EC2는 `data/`가 바인드 마운트라 DB가 살아남는다)에 올리면 INSERT가 `no such column`으로 터진다.

**테스트가 이걸 원리적으로 못 잡는다는 게 핵심이다** — 매 테스트가 새 `:memory:` DB로 시작하니 "기존 테이블이 있는 상태"가 아예 재현되지 않는다. 로컬 `data/app.db`에도 아직 `equipment` 테이블이 없어서(스모크 테스트를 안 돌렸다) 개발 중에는 영원히 안 걸릴 버그였다. 구버전 테이블을 직접 만들어 재현하는 테스트를 추가하고, 수정을 되돌려 실제로 그 예외로 실패하는 것까지 확인했다. §README_12의 "개별 함수 단위 pytest로는 못 잡는 버그가 있다"와 같은 계열인데, 이번엔 **환경 상태**가 변수였다.

**(B) 예외 타입을 열거하면 어댑터가 바뀔 때 샌다.** 참고문헌 노드는 `RuntimeError`(모델 소진)만 잡고 있었다. 그런데 호출 경로가 `recommend_references → paper_search → arxiv_api`라 arxiv가 잠깐 죽으면 `requests.RequestException`이 그대로 올라오고, **방금 LLM으로 만든 가설·설계가 체크포인트에 커밋되지 못하고 통째로 날아간다.** 주석엔 "부가 기능 실패가 핵심 결과를 막지 않는다"고 적혀 있었지만 코드는 그렇지 않았다.

여기선 `Exception`으로 넓히는 게 맞다고 판단했다 — 이 노드의 계약이 "무슨 일이 있어도 앞 단계 산출물을 지킨다"이고, 타입을 열거하면 어댑터를 갈아끼울 때마다 목록이 새는데 **새는 방식이 하필 "핵심 결과 소실"**이기 때문이다. 대신 잡은 예외 타입을 로그에 남겨 조용히 삼키지는 않는다.

**(C) 하나의 상수가 두 가지 역할을 겸하고 있으면 한쪽을 못 바꾼다.** 보유 논문 검색이 `k=max_results(5)`였는데, 논문 한 편이 100청크를 넘으니 유사도 상위 5개는 거의 항상 같은 논문의 인접 청크다. `paper_id`로 dedupe하면 1~2편만 남아 **보유 논문이 있어도 매번 외부 검색으로 넘어갔다**(`retrieve()`가 `MAX_CHUNKS_PER_PAPER`로 푼 것과 같은 성격의 문제).

고치려고 `k`를 키우다가 알아챈 게, `k`가 우연히 **결과 개수 상한** 역할도 겸하고 있었다는 것이다. 깊이만 키웠으면 참고문헌이 20편씩 나올 뻔했다. 청크 깊이(`OWNED_CHUNK_DEPTH_FACTOR`)와 논문 수 상한(`max_results`)을 별개 축으로 분리했다. 07-28의 "라벨(표시용)과 소속 판정을 같은 값에서 파생시키지 말라"와 같은 형태의 실수다 — **하나의 값이 두 요구를 겸하고 있으면 한쪽 요구가 바뀔 때 반드시 걸린다.**

한편 깊이를 키우면 "관련 없는 보유 논문"도 들어오므로 유사도 임계값을 둘지 논의했는데, **두지 않기로 했다**(사용자 결정) — 보유 논문은 사용자가 직접 등록한 것 자체가 신뢰 신호라는 기존 원칙(`retrieve()`가 논문 VDB를 무조건 신뢰하는 것)을 유지하고, 실측 없이 정한 L2 거리 상수는 근거 없는 숫자만 하나 늘리는 셈이라서다.

### 7.5 테스트 대역이 계약을 가리고 있던 두 사례

리뷰 중 **테스트가 초록불인데 검증은 안 하고 있던** 경우를 두 개 발견했다.

첫째, `references` 항목은 `source="owned"`일 때 `reasoning` 키가 없었는데(스크리닝을 안 거치니까) 테스트 헬퍼 `_ref()`가 owned에도 `reasoning=""`를 넣고 있었다. **생산 코드가 만들지 않는 모양으로 테스트를 하고 있었던 것**이라, ⑦이 `r["reasoning"]`에서 `KeyError`를 맞을 자리가 그대로 남아 있었다. 생산자가 빈 문자열로 채우도록 통일했다 — 소비자가 source별 키 차이를 기억해야 하는 규칙은 소비자가 늘수록 언젠가 깨진다.

둘째, 참고문헌 노드의 예외 처리를 검증하는 테스트에서 대역이 `def _boom(text)`였다. 노드가 `disabled_models=`를 키워드로 넘기게 바뀌자 이 대역은 의도한 예외가 아니라 **`TypeError`를 던졌는데, 그것도 `Exception`이라 테스트는 그대로 통과했다.** 엉뚱한 이유로 초록불이 되는 상태다. `**kw`를 받도록 고쳤다.

둘 다 "테스트가 통과한다"와 "테스트가 의도한 것을 검증한다"가 다르다는 사례다.

### 7.6 서킷 브레이커를 참고문헌 경로까지

`recommend_references`는 검색어 추출 1회 + 스크리닝 N회로 **워크플로우에서 LLM을 가장 많이 부르는 지점**인데, `disabled_models`를 받지도 돌려주지도 않고 토큰도 버리고 있었다. RoadMap 08-12 항목이 "`paper_screening`은 별개 배치 파이프라인이라 서킷 브레이커 범위 밖"이라 적어둔 게 있었지만, 그건 cron/배치에서 부를 때 얘기였고 지금은 `disabled_models`를 이미 들고 다니는 그래프 안이라 전제가 다르다.

고치면서 알게 된 건, 이게 **단계 간 문제가 아니라 한 번의 호출 안에서도 낭비**였다는 점이다 — 검색어 추출에서 gemini가 죽어 claude로 fallback해도 그 사실이 버려지니, 이어지는 후보 N개가 **매번 gemini부터 다시 때려보고 실패**한다. `screen_candidate()`에 선택 인자로 추가(기본 `None`이라 ③ 배치 경로는 무영향)하고, `recommend_references()`가 `(목록, disabled_models, tokens_used)` 3튜플로 반환하게 했다.

겸사겸사 `_add_tokens`가 `graph.py`·`research_workflow.py`에 같은 코드로 있고 여기가 세 번째가 될 참이라 `models.add_tokens`로 올렸다 — 토큰은 모델 호출의 부산물이므로 "모델 정책은 `models.py` 단일 지점" 규칙에 속한다.

### 7.7 판단이 갈렸던 네 지점 — 버린 안과 그 근거

위 항목들 중 **다른 선택지가 실제로 그럴듯했던** 네 개는 무엇을 버렸는지까지 남긴다. 채택안만 적으면 나중에 "왜 이렇게 안 했지?"를 다시 처음부터 따지게 된다.

#### (C) 보유 논문 검색 — 왜 `doc_type` 필터가 아니라 `k` 확대인가

버린 안 세 개:

- **`doc_type`을 `summary`/`abstract`로 필터**: 논문당 문서가 1~2개라 청크 쏠림이 원천적으로 사라진다. 처음 떠올린 안이었고 곧 뒤집었다 — **요약은 lazy 생성**이라 방금 등록한 논문은 `fulltext_chunk`밖에 없다. 필터를 걸면 그 논문은 참고문헌 후보에서 통째로 빠진다. "요약이 우연히 생성돼 있는 논문만 인용될 수 있다"는, 논문 내용과 무관하고 사용자가 알 수도 없는 기준이 생긴다.
- **`MAX_CHUNKS_PER_PAPER`식 논문당 상한**: `retrieve()`가 같은 증상을 이걸로 풀었으니 대칭처럼 보이지만, 여긴 **이미 dedupe로 논문당 1개로 접고 있다**. 문제는 *출력*에서 한 논문이 자리를 먹는 게 아니라 *입력 창(k)*이 좁은 것이라 상한을 더 걸어도 아무것도 안 바뀐다. 증상이 같아도 원인이 다른 경우.
- **유사도 임계값(거리 컷)**: §7.4 마지막 문단 참고.

`k`를 키우는 비용이 거의 0이라는 점도 판단에 들어갔다 — 쿼리는 `k`와 무관하게 **한 번만** 임베딩되고 Chroma는 어차피 컬렉션 전체와 거리를 계산한다. `k`는 그중 몇 개를 실제로 꺼내올지만 정하므로, 100개를 꺼내도 로컬 메모리 복사 수준이다. 배율 20은 실측(122청크/논문) 기반 대략치다.

#### (G) 장비 이름 매칭 — 왜 정교화하지 않았나

**단어 경계(`\b`) 매칭을 버린 결정적 이유는 한국어 문법이다.** 파이썬 `re`의 `\b`는 `\w` 경계에서 성립하는데 한글 음절은 유니코드에서 `\w`다. 조사가 명사에 그대로 붙는 한국어에서는 `\b레이저\b`가 `"레이저를 사용한다"`를 **매칭하지 못한다**("를"도 단어 문자라 경계가 안 생김). 즉 정교화하려던 방식이 정상적인 한국어 문장에서 오히려 못 찾는다.

더 근본적으로, 두 방식은 **틀리는 방향이 다르고 그 둘은 대칭이 아니다**:

| 방식 | 틀릴 때 | 결과 |
|---|---|---|
| 부분 문자열 | 과검출 — "레이저"가 "레이저 거리계"에도 걸림 | 관계없는 주의사항이 하나 더 보임 |
| 단어 경계 | 미검출 — "레이저를"을 못 잡음 | **안전 경고가 안 뜸** |

안전 가드레일에서 감수할 수 있는 건 앞쪽이다. 그래서 실제로 고친 건 **빈 이름 가드 하나뿐**이다 — 파이썬에서 `"" in "아무 텍스트나"`는 `True`라, `name=""`인 행이 있으면 그 주의사항이 모든 실험 설계에 붙는다(`NOT NULL`이어도 `""`는 통과하므로 실제로 가능한 상태).

다만 과검출에도 대가는 있다: **관계없는 경고가 매번 뜨면 사람이 경고를 안 읽게 된다.** 그게 관찰되는 시점이 매칭 규칙 정교화의 착수 시점이다.

#### (F) 서킷 브레이커 — 반환 형태와 공유 함수 수정 범위

**반환 형태**는 3튜플 `(목록, disabled_models, tokens_used)`을 택했다. `invoke_with_fallback`의 4튜플과 같은 모양이라 저장소 안에서 눈에 익는다는 게 이유다. 버린 안: (a) 호출자 리스트를 제자리 수정 — `models.py`가 `disabled_models = list(...)`로 **방어적 복사**를 명시해 "호출자 원본은 안 건드린다"는 경계를 세워뒀는데 반대로 가는 셈이다. (b) dict 반환 — `screen_candidate`가 그렇게 하지만 그건 주 산출물 자체가 레코드라서다. 여긴 주 산출물이 목록이라 dict에 넣으면 모든 호출자가 어차피 꺼내야 한다.

**공유 함수(`screen_candidate`)를 건드릴지**가 진짜 판단이었다. 이 함수는 ③ 추천 검색과 공유하고, RoadMap 08-12에 "`paper_screening.py`는 별개 배치 파이프라인이라 서킷 브레이커 범위 밖"이라고 이미 적혀 있었다. 그 기록을 뒤집은 근거: **그 문장은 cron/배치에서 부를 때 얘기**였고 지금은 `disabled_models`를 이미 들고 다니는 그래프 안이라 전제가 다르다. 그래도 위험을 줄이려고 **덧붙이는 방식**(기본값 `None`인 선택 인자 + 반환 dict에 키 하나 추가)을 택했다 — `paper_recommend.py`는 이 인자를 안 넘기므로 동작이 완전히 동일하다(코드로 확인).

버린 안: **검색어 추출 호출에만 적용** — 절약이 가장 작은 곳(1회)만 고치고 정작 N회는 그대로 두는 셈이라 의미가 없다.

**알려진 한계(주석 정정)**: 스크리닝이 `RuntimeError`를 던지는 경로에서는 그 호출에서 쌓인 `disabled_models`를 못 건진다 — `invoke_with_fallback`이 재귀하며 쌓은 목록이 예외와 함께 스택에 묻히기 때문. 처음 단 주석은 "여기서 죽은 모델도 이어간다"고 적었는데 **사실이 아니어서 고쳤다.** 예외에 데이터를 실어 보내는 건 정상 경로가 아닌 곳에 데이터를 태우는 설계라 안 했고, 이 `RuntimeError`는 애초에 전 모델 소진일 때만 나오므로 남은 후보도 어차피 다 실패해 실질 손해가 없다.

#### (J) 설계 프롬프트에 `testable_prediction`

끊겨 있던 지점: `generate_hypothesis`가 `testable_prediction`을 만들고 `analyze_results`가 그걸 채점 기준으로 쓰는데, **사이에 낀 `design_experiment`가 그 값을 못 보고 있었다.** 만들어둔 값을 그냥 안 쓰던 상태다.

실질 피해가 큰 이유는 **두 단계 사이에 사람이 실험실에서 실제 실험을 한다**는 점이다. 예측을 판별하지 못하는 설계가 나오면 사람이 며칠 걸려 실험한 뒤에야 "판단하기 불충분 → 재설계"가 나온다. 낭비되는 게 LLM 호출이 아니라 사람의 실험 시간이다.

값을 human 메시지에 넣는 것에 더해 시스템 프롬프트에 "그 예측이 실제로 측정 가능하도록 설계하라"는 지침을 함께 넣었다 — 값만 던지면 참고 자료로 흘려볼 수 있고, `ExperimentDesign` 스키마에는 "이 예측을 어떻게 판별할 것인가"를 담을 필드가 없어 **제약을 걸 수 있는 자리가 지침문뿐**이었다. 스키마에 필드를 새로 추가하는 안은 버렸다 — 소비자가 없는 구조화 필드를 미리 만드는 셈이고, 판별 방법은 이미 `procedure`가 담아야 할 내용이며, 필드를 늘리면 LLM은 반드시 채우고 모르면 지어낸다(`paper_extraction.py`에서 이미 겪은 것).

**검증 한계**: 이 변경은 실제 LLM으로 안 돌려봤다. 테스트는 예측 문자열이 프롬프트에 들어갔는지만 확인한다 — 설계 품질이 실제로 좋아졌는지는 돌려봐야 안다.

### 7.8 남긴 것

- **UI 없음**: ⑤⑥ 둘 다 백엔드만이고 라이브러리 탭도 워크플로우 화면도 없다(사용자 결정). 엔드포인트가 이미 있어 UI는 순수 연결 작업이라 분리해도 안전하고, ⑦까지 화면이 더 늘어난 뒤 **한 번에** 붙이면서 그 시점에 Streamlit 유지 vs React 전환도 같이 판단한다. `research_workflow.py`는 그래서 아직 `main.py`에 안 붙어 있고, 지금 이 그래프를 컴파일해 쓰는 건 `__main__` 스모크 테스트와 pytest뿐이다.
- **재생성 시 references 누적**: 같은 stage를 다시 돌면 산출물은 덮어써지는데 `references`는 덧붙기만 해서 폐기한 가설로 찾은 논문이 남는다. ⑦이 이 목록을 "목록에 없는 인용은 환각 신호"의 기준으로 쓸 예정이라 그 전에 정해야 한다 — 다만 "재생성"과 "그냥 다시 실행"을 그래프가 구분하려면 UI가 의도를 실어 보내야 하고 그 UI가 아직 없어서, 지금 정책부터 만들면 순서가 거꾸로다. 근거와 후보안은 RoadMap 설계 노트에 남겼다. **(08-05 결정됨 — 후보 (b) `superseded` 표시로 확정. 근거는 RoadMap 설계 노트 "열린 질문 — 재생성 시 references 누적" 참고.)**

## 8. EC2 배포 트랙 폐지 (08-05 결정)

**§4·§6과 달리 이건 코드 문제가 아니라 "결정의 전제가 하위 항목까지 안 내려간" 문제였다.** 08-05에 RoadMap 전반을 검수하다 나왔다.

### 8.1 발견

08-04에 이 프로젝트는 **싱글유저 로컬 앱**으로 확정됐다 — "다운로드해서 각자 자기 컴퓨터에서 쓰는 것". 그런데 `.github/workflows/deploy.yml`은 그 뒤로도 `main` push마다 EC2로 `scp`+`ssh` 배포를 계속 하고 있었고, **그 EC2 인스턴스가 이제 무엇을 위해 도는지가 로드맵 어디에도 적혀 있지 않았다.**

이게 그냥 죽은 설정이 아니라 **파생 비용을 만들고 있었다**는 게 핵심이다. `deploy` job이 `runs-on: ubuntu-24.04-arm`으로 고정된 유일한 이유가 EC2(Graviton, arm64)였고, `docker/build-push-action`에 `platforms:` 지정이 없어서 **러너의 네이티브 아키텍처로만 이미지가 빌드**됐다 — 즉 `quart512/science-chatbot:latest`가 **arm64 전용**으로 Docker Hub에 올라가고 있었다. 로컬 배포판을 받을 사용자 대부분(Windows PC·Intel Mac·일반 x86_64 Linux)이 이 이미지를 못 돌리거나 QEMU 에뮬레이션으로 억지로 돌려야 한다는 뜻이다.

### 8.2 결정

사용자 답이 명확했다 — **"EC2를 처음 써봐서 남긴 메모였고, 앞으로 EC2는 랜딩페이지와 다운로드 페이지만 서빙한다."** 배포 트랙 폐지 확정.

폐지의 파생 효과 셋:

1. **멀티아키텍처 항목이 단순해졌다.** EC2가 없으면 arm64 러너를 쓸 이유가 사라진다 — "EC2용 push와 배포판용 push를 겸할지 분리할지"라는 설계 문제가 통째로 없어지고, **러너를 x86_64로 되돌리고 `platforms: linux/amd64,linux/arm64`를 추가**하는 것만 남는다.
2. **라이브 검증 체크리스트 §D의 `equipment` 스키마 마이그레이션 항목이 해소됐다.** 이 항목이 §D("배포 환경에서만 드러나는 것")에 있던 이유가 "EC2의 `data/app.db`에 구 스키마가 남아있을 수 있는데 로컬에선 재현이 안 된다"였는데, 그 DB가 배포 대상에서 빠졌다. 로컬 배포판 사용자는 전부 빈 `data/`에서 시작하므로 구 스키마가 존재할 수 없다.
3. **`docs/DEPLOY.md` 정리 방향이 바뀐다.** 예정 표 `최종` "문서 정리"에 "deploy ec2랑 로컬 둘로 나누기"라고 적혀 있었으나, 나눌 두 갈래 중 하나가 사라졌으므로 **로컬 배포판 절차 하나로 다시 쓰는 것**이 맞다. EC2 쪽은 랜딩/다운로드 페이지 서빙 절차만 남는다.

`deploy.yml` 수정은 **두 갈래로 나눠 처리했다.** 원래는 둘 다 릴리즈 게이트 착수 시점으로 미룰 계획이었으나, 앞쪽은 미룰 이유가 없어 이번에 바로 했다.

- **scp/ssh 두 스텝 제거 — 08-05에 바로 처리.** 미루면 `feature/single_user`가 `main`에 머지되는 순간 워크플로우가 **랜딩/다운로드 페이지 전용으로 용도가 바뀐 EC2에 `docker compose pull && up -d`를 다시 실행해 앱을 되살린다** — 방금 내린 폐지 결정과 정면으로 충돌한다. 머지가 릴리즈 게이트 뒤라 순서상 사고가 나기 전이긴 하지만, 폐지하기로 한 경로를 굳이 살려둘 이유가 없어 결정과 같은 날 반영했다. job 이름도 `deploy` → `publish`로 바꿨다 — 이 job이 실제로 하는 일은 Docker Hub에 이미지를 올리는 데서 끝나고 그 뒤는 CI 밖이라, `deploy`라는 이름을 남겨두면 **이번 검수에서 문제 삼은 바로 그 "낡은 이름이 낡은 전제를 실어 나르는" 패턴**을 그대로 반복하게 된다.
- **러너·`platforms` 변경은 릴리즈 게이트로 남김.** buildx·QEMU 설정을 같이 바꾸고 실제로 두 아키텍처 이미지가 올라가는지 확인해야 하는 별개 작업이라 분리했다. 지금은 `runs-on: ubuntu-24.04-arm`이 그대로 남아 있고 **그 이유가 무엇이었는지·왜 지금은 틀렸는지를 워크플로우 주석에 적어뒀다**(EC2가 없어진 지금 arm64 러너는 근거가 없고, 오히려 이미지를 arm64 전용으로 만드는 원인이다).

Docker Hub 빌드·push 스텝은 배포판 이미지용으로 **그대로 필요하므로 워크플로우를 통째로 지우지는 않았다.**

### 8.3 이번 검수가 남긴 규칙

08-05에 이미 한 번 "예정 표 검수"를 돌려 **"큰 이관 작업(React 전환) 뒤에는 백로그도 같이 훑어야 한다"**는 교훈을 적어놨었다. 그런데 정작 **더 큰 전환인 08-04 싱글유저 확정에는 그 검수를 안 돌렸다** — 그래서 EC2 트랙뿐 아니라 "로깅 → 그걸로 모델 튜닝"(배포판 사용자의 로그는 저자가 모을 방법이 없다), `t4g.micro` 제약의 근거(실행 기계가 사용자 노트북으로 바뀜) 같은 것들이 옛 전제 위에 그대로 떠 있었다.

**규칙: 전제를 바꾸는 결정을 내렸으면, 그 전제 위에 쓰인 항목을 그날 전부 훑는다.** 교훈을 적어두는 것과 실제로 적용하는 것은 별개라는 게 이번에 확인된 부분이다.

## 9. RoadMap "설계 노트 · 열린 질문" 정리 이관 (08-06)

RoadMap.md가 721줄까지 늘어나 사용자가 정리를 요청했다. 완료 표·예정 표는 각각 실행 이력 원장·활성 백로그라 손대지 않고, "설계 노트 · 열린 질문"(당시 446줄, 문서에서 가장 큰 섹션) 중 **(a) 스스로 폐기·해소를 이미 선언했거나 (b) 이미 구현 완료됐고 살아있는 예정 항목이 더는 참조하지 않는** 것만 골라 옮겼다. 기준에 안 맞아 그대로 둔 것도 있다 — 예를 들어 "부록: 프론트 통합 참고자료"는 옛 자료처럼 보였지만 예정 표의 "[랜딩] 랜딩/다운로드 페이지 구축" 항목이 "그대로 유효"라고 명시적으로 참조하고 있어 남겼다.

### 9.1 abstract 처리 설계 3연작 (07-28~07-29, 구현 완료)

**abstract와 ②a의 관계 (07-28)** — "abstract만 있으면 요약기가 필요 없지 않나?"에 대한 답:

- **abstract는 `PaperExtraction` 다섯 필드 중 `core_claims` 하나만 커버한다.** `author_stated_limitations`는 Discussion·Limitations 절에, `unresolved_questions`는 Conclusion·Future Work에, `code_data_availability`는 Data Availability 문단·각주에, `evidence`의 조건·규모(표본 크기·파라미터)는 Methods에 있다 — 넷 다 구조적으로 본문에만 있다.
- 이건 우연이 아니라 초록의 장르적 성격이다: **초록은 읽게 만들려고 쓰는 글이라 주장은 강하게 쓰고 유보는 본문에 둔다.** abstract만으로 요약하면 저자의 헤지를 통째로 잃는데, 그건 "저자가 스스로 밝힌 한계를 추출한다"는 이 프로젝트의 핵심 가치와 정반대다. → **②a는 abstract의 대체가 아니라 보완이다.** 스키마·파이프라인 재편 불필요.
- 다만 **지금 abstract를 그냥 버리고 있다**: `arxiv_search()`가 주는데 `_BIBLIOGRAPHIC_WHITELIST`에서 빠져 저장되지 않는다. 화이트리스트의 원래 의도는 "청크 122개에 1~2천 자를 복제하지 말자"였지 "버리자"가 아니었다 → **한 번만 저장**하면 해결.
- abstract를 저장할 값어치: 요약이 lazy 생성이라 **등록 직후~요약 생성 전까지 보여줄 게 없는 공백**이 있는데, 저자가 쓴 abstract가 그 구간을 공짜로 메운다(라이브러리 목록·RAG 검색 양쪽). 요약 생성이 실패한 논문(`_PERMANENTLY_FAILED`)에도 최소한의 표시가 남는다.
- **검증은 "주장 대조"가 아니라 "제목 일치"로**: abstract와 추출된 `core_claims`를 대조해 검증하자는 발상은 불일치 원인이 (a) 추출 오류 (b) 초록이 본문과 다른 걸 강조 (c) PDF가 v1이고 arxiv 기록은 v3 — 셋 다 흔해서 신호의 정밀도가 낮고, 비교하려면 LLM을 또 불러야 한다. 반면 제목 문자열 비교는 결정론적·고정밀이고 실제 사고(id 오입력·다른 논문 업로드)를 잡는다.

**abstract·summary 저장 위치 — RDB·VDB 이중 저장 (07-30, 논의 중 정정)**:

- "abstract도 summary도 둘 다 VDB에 넣어야 하나, RDB(카탈로그)면 안 되나?"에 대한 답은 "abstract는 RDB만"이 아니다 — **summary와 같은 이중 저장**이 맞다. 처음엔 abstract의 용도를 단일 저장·추출 프롬프트 앵커·제목 검증(전부 `paper_id` 정확 키 조회)뿐이라고 봤는데, 위 "abstract와 ②a의 관계" 절이 이미 적어둔 "라이브러리 목록·**RAG 검색** 양쪽"을 놓치고 있었다.
- **abstract가 의미 검색에도 필요한 이유**: summary는 lazy 생성이라 등록 직후엔 없는 경우가 흔하다. 그 공백 동안 QA가 참고할 게 fulltext_chunk(500자 조각)뿐인데, 저자가 쓴 abstract는 (1) 그 공백을 메우고 (2) 우리가 LLM으로 뽑은 summary보다 원문 그대로라 신뢰도가 높다. 그러니 abstract도 QA의 `similarity_search_with_score`에 걸리도록 **VDB에 임베딩된 채로 있어야** 한다.
- **VDB 저장 방식은 summary와 동일한 패턴** — `doc_type="abstract"`로 **논문당 문서 1개**(`ids=[f"{paper_id}-abstract"]`)만 만든다. `_store_summary()`(paper_ingest.py 280~293줄)가 이미 이 패턴이다: 별도 문서 하나에 텍스트(임베딩용)와 메타데이터를 같이 넣는 방식. **청크 메타데이터에 끼워 넣는 것과는 다르다** — 07-28에 겪은 복제 문제(`_BIBLIOGRAPHIC_WHITELIST` 도입 이유)는 서지정보를 `fulltext_chunk` 청크마다(`**bib_meta`로 병합) 반복해서 넣는 방식 때문이었지, "VDB에 문서를 만드는 것" 자체의 문제가 아니었다. `_store_summary()`처럼 논문당 1개 문서로 만들면 청크 수와 무관하게 복제가 없다.
- **RDB(논문 카탈로그, 6-6)에도 남긴다** — 프롬프트 앵커·제목 검증·목록 표시는 여전히 `paper_id` 정확 키 조회라 카탈로그가 더 잘 맞는다(임베딩 모델 로딩 없이 바로 조회).
- 결론: abstract는 RDB(정확 키 조회용)와 VDB(`doc_type="abstract"` 단일 문서, 의미 검색용) **둘 다에** 저장. summary도 이미 같은 이중 성격(구조화 데이터는 메타데이터로, 텍스트는 임베딩으로)이라 새로운 패턴이 아니다.
- 남은 문제: `_fetch_summary()`의 캐시 확인은 벡터 연산이 전혀 없는 순수 메타데이터 필터(`vectorstore.get(where=...)`)인데도 Chroma 객체를 만들어야 해서 bge-m3가 로드된다(read 커맨드 실행해도 로딩바가 뜨는 이유). 이 접근 패턴만 보면 RDB가 더 잘 맞지만, 캐시 확인이 핫 패스가 아니라서 지금 당장 이걸 이유로 이중 저장(요약 완료 여부 플래그를 카탈로그에도 두기)까지 할 값어치가 있는지는 미정 — 6-6 카탈로그 스키마 설계 시 재검토.

**6-3b① 실제 구현 + 답변 근거 표시 (07-29)** — 위 두 절의 결정대로 VDB 쪽(`doc_type="abstract"` 단일 문서)을 구현. RDB(카탈로그) 저장은 6-6 몫으로 아직 안 함. 구현 중 파생된 결정 세 가지:

- **답변 근거는 LLM이 아니라 결정론적으로 표시한다**: `graph.py`의 `describe_context_sources()`가 `state.context`의 메타데이터(paper_id/doc_type/title, source)만 보고 파인만·논문(제목+전문발췌/요약/초록)·웹검색 목록을 만들어 `final_answer()`의 `comment`에 붙인다. `verified`나 `final_answer_structure`에 필드로 넣지 않은 이유: "결정론적으로 계산 가능한 값은 LLM 스키마에 넣지 않는다"(설계 원칙)와 같은 논리 — 이미 아는 사실(어떤 문서가 context에 들어왔는지)을 LLM에 다시 판단시키면 비용과 환각 위험만 생긴다. 대신 "실제로 답변이 그 문서를 썼는지"는 일부러 안 보여준다 — `generate()`가 "문서가 무관하면 무시해라"를 허용하므로 그건 비결정론적 판단이 필요해 이 함수의 책임 밖으로 뒀다(②a·②b의 "판정 아니라 추출" 원칙과 같은 결).
- **summary 문서도 title 등을 받는다**: `_fetch_bib_meta()`를 신설해 이미 `fulltext_chunk`에 복제돼 있던 서지 필드(`_BIBLIOGRAPHIC_WHITELIST`)를 꺼내 `_store_summary()`에 같이 넣는다 — `get_paper_summary()`가 `bibliographic`을 안 받는 별도 호출이라 처음엔 "더 큰 리팩터가 필요하다"고 잘못 판단했었는데, 실제로는 그 데이터가 이미 Chroma에 있어서(청크마다 복제돼 있음) 그냥 읽어와 재사용하는 정도로 충분했다.
- **arxiv_id만 있고 bibliographic이 없으면 자동으로 채운다**: `arxiv_api.py`에 `fetch_by_id()`(id_list 조회)를 신설 — `arxiv_search()`(키워드 검색)로 제목 등을 다시 찾으면 다른 논문이 걸릴 위험이 있으므로, 이미 아는 `arxiv_id`는 정확히 그 id로만 조회한다. `register_paper()`가 abstract가 없을 때만 호출(호출자가 이미 서지정보를 줬으면 조회 안 함), 호출자 명시값이 항상 우선, 조회 실패는 등록을 막지 않는다. 이로써 `register_paper()`가 "LLM 호출은 없다"에서 "네트워크 호출은 있을 수 있다"로 성격이 살짝 바뀌었다(스로틀 3초 있음, `arxiv_api.py`).
- **남은 한계**: `bibliographic` 없이(그리고 `arxiv_id`도 없이) 등록된 논문(해시 기반 `paper_id`)은 위 자동 조회 대상도 아니라서 여전히 title이 없다 — 데이터 자체가 없는 경우라 지금 범위에서 해결할 방법이 없다(근거 표시는 이 경우 `paper_id`로 폴백).

### 9.4 Docker 패키징 재검토 — Tauri/Electron 재론 → 기각 전 과정 (08-05, 전부 실측)

RoadMap.md엔 최종 결론(Electron 기각, portable 파이썬 번들 확정)만 압축해 남기고, **실측 수치와 기각한 대안의 상세 근거**는 여기로 옮긴다. 네 개의 노트가 순서대로 재검토를 거듭한 기록이다.

**① Docker 패키징 재검토 — Tauri/Electron 재론**: "Docker Desktop 설치 진입장벽이 너무 크다, 타우리나 일렉트론 같은 다른 옵션은 없나"라는 질문으로 08-04 패키징 결정을 다시 열었다. **결론: Tauri/Electron은 이 문제의 절반만 풀고, 나머지 절반(torch)을 먼저 풀지 않으면 그 절반조차 08-04에 기각한 그 이유로 다시 막힌다.**

- **진입장벽은 두 겹이고 Tauri/Electron은 한 겹만 없앤다 (실측)**: ① Docker Desktop 설치 ~600MB~1GB + WSL2 설정(Windows) + 관리자 권한 → **없앤다**. ② 앱 이미지 pull 481MB(압축, 디스크 2.21GB) → 그대로. ③ `bge-m3` 런타임 다운로드 **2.1GB**(HF 캐시 실측, safetensors 단일 파일 기준) → 그대로. **첫 실행 다운로드가 어느 길로 가든 ~2.6GB**라는 뜻 — 체감 벽(관리자 권한·WSL2·낯선 시스템 도구)은 확실히 사라지지만 용량은 안 준다.
- **Docker를 실제로 없애는 조합은 하나뿐**: "셸만 Tauri/Electron + 백엔드는 Docker"는 **설치할 게 둘로 늘어** 목표에 정반대라 폐기(08-05 노트가 이미 구분해둔 갈래). 남는 건 **"셸 + PyInstaller/Nuitka로 얼린 파이썬 사이드카"**이고, 이게 정확히 08-04가 기각한 것이다. **기각 사유(torch·transformers·chromadb 얼리기)는 지금도 유효하고, 08-04에 안 적힌 비용이 하나 더 있다** — 얼린 바이너리는 **플랫폼마다 따로 빌드·검증해야 한다**(Windows/macOS arm64/macOS x64/Linux 4종 CI 매트릭스). 게이트 ②(Windows 스크립트 하나)도 아직 못 하는 상태에서 검증 대상이 4배가 된다.
- **판을 바꾸는 한 수는 torch 제거다.** site-packages 최대가 `torch` 519MB인데 **앱 코드는 torch를 단 한 줄도 직접 안 쓴다**(`grep` 0건) — 오직 `retrieval.py:10`의 `HuggingFaceEmbeddings` → `sentence-transformers` 경로로만 들어온다. **임베딩 접점이 파일 하나의 한 줄.** 게다가 `onnxruntime`은 이미 깔려 있고(chromadb가 `ONNXMiniLM_L6_V2` 기본 임베딩으로 제공) onnxruntime 경로 자체가 in-tree에서 이미 검증돼 있다. torch를 걷어내면 torch+transformers+sympy+sklearn(+scipy) **650MB 이상**이 빠지고 **동시에 PyInstaller 기각 사유의 대부분이 사라진다** — 즉 용량 개선이자 Tauri/Electron 경로를 여는 **선행 조건**이다.
- **Tauri vs Electron — 이 저장소에선 통념이 뒤집힌다.** 보통은 "Tauri가 훨씬 가벼우니 Tauri"인데, **셸 크기 차이(~10MB vs ~150MB)가 2GB 넘는 페이로드 앞에서 노이즈**라 Tauri의 주 무기가 무력화된다. 반면 Rust 학습 비용은 그대로고 Electron은 `frontend-react`로 이미 쓰는 TS/JS다. **간다면 Electron이 맞다.**
- **권고 순서**: ① 게이트 ④⑤(`.env`·배포용 compose)를 먼저 — 어느 길로 가든 필요하고 지금 배포판은 제3자가 받으면 첫 줄에서 죽는다. ② torch→onnxruntime 조사 — 이건 "Electron으로 갈까"의 **선행 판단**이지 별개 작업이 아니다. 되면 Electron 경로가 열리고 Docker판도 같이 가벼워진다(양쪽 다 이득), 안 되면 08-04 기각 근거가 살아있으니 Docker 유지 + 첫 실행 경험 개선으로 방향 전환. ③ Electron 착수는 ②의 결과를 보고. **지금 당장 Electron/Tauri부터 착수하는 건 권하지 않는다.**

**② torch 제거 가능성 조사 — 결론: 가능하다, 재색인도 불필요**: 위 선행 조건을 실제로 조사했다. **다섯 가지 다 통과했고 예상보다 훨씬 깨끗하다.**

- **① 공식 ONNX 익스포트가 있다** — `BAAI/bge-m3` 저장소에 `onnx/model.onnx` + `onnx/model.onnx_data`가 정식으로 포함돼 있다(`list_repo_files`로 확인). 직접 익스포트할 필요 없음.
- **② 파이프라인이 단순하고, 실은 직접 구현할 필요조차 없다** — `modules.json`·`1_Pooling/config.json` 실측: `Transformer(XLM-R-large) → Pooling(CLS 토큰) → Normalize(L2)`가 전부다(`pooling_mode_cls_token: true`, 평균 풀링 아님, `max_seq_length: 8192`). **더 좋은 건 ONNX 익스포트의 출력이 `['token_embeddings', 'sentence_embedding']` 두 개라는 것** — `sentence_embedding`은 **이미 CLS 풀링과 L2 정규화까지 끝난 값**이다(norm 실측 1.0). 즉 구현이 "토크나이즈 → `session.run` → `out[1]`"로 끝나고 풀링·정규화 코드를 직접 안 짜도 된다(직접 짠 CLS+정규화 버전과 익스포트 내장 버전 둘 다 검증했고 결과가 같다).
- **③ 벡터가 torch와 사실상 동일하다 — 기존 `chroma_db` 재색인 불필요.** 이게 `CLAUDE.md §5`("ingest.py와 검색 경로가 반드시 같은 모델") 제약이 걸린 유일한 리스크였다. 캐시된 torch 모델로 기준 벡터를 뽑고(한국어 3 + 영어 1 문장) ONNX 결과와 비교: **코사인 유사도 최소 0.999999934, 전체 최대 절대 오차 3.24e-07**(익스포트 내장 `sentence_embedding`은 1e-8 수준으로 더 정확). **문장 간 유사도 행렬 차이도 1.92e-07** — 검색 순위가 보존된다는 직접 증거다. float32 정밀도 수준이라 재색인 없이 갈아끼울 수 있다.
- **④ 새로 추가할 의존성이 0개다.** `uv tree --invert`로 확인 — `onnxruntime`은 `chromadb`와 `pymupdf-layout`이, `tokenizers`는 `chromadb`가 **이미** 끌어온다. torch를 빼도 둘 다 남는다. `tokenizers`만으로 bge-m3 토크나이저를 로드해 한국어 문장을 실제로 인코딩하고, 그 시점에 `torch`·`transformers`가 `sys.modules`에 없음까지 확인했다.
- **⑤ 빠지는 용량 731MB** — `torch` 519M + `scipy` 81M + `transformers` 56M + `sympy` 42M + `sklearn` 33M. 전부 `sentence-transformers`(또는 torch) 경로로만 들어오는 것들이라 `sentence-transformers` + 직접 `torch` dep + `langchain-huggingface`를 빼면 같이 사라진다. `networkx`는 `pymupdf-layout`도 쓰므로 남는다.
- **⚠️ 단, 첫 실행 다운로드는 안 줄어든다** — ONNX 가중치 2161.8MB vs `pytorch_model.bin` 2165.9MB로 **사실상 동일**하다. 이 작업은 "런타임 731MB 제거"이지 "첫 실행 2.6GB 완화"가 아니다. 모델 다운로드까지 줄이려면 **int8 양자화 ONNX**(~550MB) 같은 별개 선택지가 필요한데, 그건 가중치가 실제로 바뀌므로 **재색인이 필요하다** — "재색인 불필요"는 fp32 ONNX에 한한 결론이다. 별도 판단거리로 남긴다.
- **접점**: `retrieval.py:10` 한 줄(`HuggingFaceEmbeddings(model_name="BAAI/bge-m3")`)을 커스텀 `Embeddings` 구현으로 교체. 앱 코드는 torch를 직접 import하는 곳이 **0곳**이다(`grep` 확인). `ingest.py`도 같은 모델을 쓰므로 같이 갈아끼워야 한다.
- **이게 Electron 판단에 주는 함의**: torch가 빠지면 남는 무거운 의존성이 `onnxruntime`·`pymupdf`·`chromadb`(rust bindings)·`tokenizers`(rust)로 **전부 컴파일된 확장 모듈**이다 — PyInstaller가 어려워하는 건 torch의 방대한 dylib 세트와 동적 임포트였지, 컴파일된 `.so`/`.dylib` 수집은 오히려 잘 다루는 영역이다. **08-04의 "파이썬 얼리기가 까다롭다"는 기각 근거가 torch 제거 후에는 상당 부분 무력화된다.**

**③ Electron 검토 — 결론: Electron은 필요 없다, portable 파이썬 번들이면 Docker가 사라진다**: torch 제거 후 "Docker Desktop 진입장벽을 없애려면 Electron/Tauri로 가야 하나"를 다시 봤다. **답은 "그 축이 아니다"**였다.

- **실측 — Docker도 PyInstaller도 Electron도 없이 앱이 완전히 돈다.** uv가 쓰는 독립 실행 파이썬(python-build-standalone)과 `site-packages`를 **전혀 다른 경로로 복사**한 뒤 venv 없이 `PYTHONPATH`만 주고 실행: `GET /api/health` 200, `GET /` 200(React SPA 서빙), `GET /api/papers` 200(chromadb+SQLite 경유). **08-04가 기각한 "파이썬 얼리기(PyInstaller)"를 할 필요 자체가 없다** — A1111·ComfyUI의 Windows 포터블 방식(임베디드 인터프리터 + 설치된 패키지를 폴더째)이 그대로 통하고, torch가 빠지면서 현실적인 크기가 됐다.
- **용량 실측**: 독립 파이썬 75MB + site-packages, 압축 후 번들 **236MB**. 현재 Docker 이미지(압축 266MB)와 거의 같으면서 **Docker Desktop 설치(~1GB + 관리자 권한 + WSL2)가 통째로 사라진다.** 모델 2.1GB는 어느 안에서도 동일.
- **핵심 판단 — Docker 제거와 Electron 도입은 별개의 축이다.** Docker를 없애는 레버는 **파이썬 배포 방식**(portable 번들)이고 Electron과 무관하다. Electron이 주는 건 "브라우저 탭 대신 네이티브 창"뿐이라 통증이 아니라 화장이다. 사용자가 말한 통증(Docker Desktop)은 번들만으로 100% 해결되고, **기존 자산이 그대로 재활용된다** — `start.command`/`start.bat`은 `docker compose up` 자리를 파이썬 실행으로 바꾸면 되고 08-05 PWA manifest도 그대로 "앱으로 설치"를 띄운다. 덤으로 "탭을 닫아도 컨테이너는 계속 산다"도 사라진다(백엔드가 실행 스크립트의 자식 프로세스라 수명 관리가 오히려 단순).
- **Electron을 지금 안 하는 진짜 이유 — 서명 비용.** 플랫폼 4종 빌드는 **어느 쪽을 골라도 발생한다**(pymupdf·onnxruntime·chromadb rust bindings·tokenizers가 전부 컴파일된 확장이라 플랫폼별 wheel 필요) — 이게 Docker의 "한 번 빌드하면 어디서나"를 포기하는 값이다. 그런데 **Electron만 추가로 무는 게 있다**: macOS `.app` 번들은 **서명·공증(notarization)** 없이는 Gatekeeper가 "손상됐다"며 막고(Apple Developer 연 $99), Windows는 SmartScreen 경고가 뜬다(코드 서명 인증서 유료). `.command` 셸 스크립트는 Gatekeeper가 훨씬 관대하다. **즉 Electron은 진입장벽 하나(Docker)를 없애고 다른 하나(서명 경고)를 들여오는 셈**이라 순이득이 작다.
- **권고 — 2단계로 나눈다.** ① **portable 번들 + 기존 스크립트 + PWA**(Docker Desktop 제거, Electron 불필요, 비용은 플랫폼 4종 빌드 CI). ② **Electron은 선택, 나중** — 브라우저를 아예 안 거치고 싶거나 자동 업데이트가 필요해지면. **PWA로 먼저 써보고 실제로 불편하면 얹는 구조라 먼저 만든 게 아무것도 안 버려진다**("단순 경로부터" 원칙).
- **Tauri는 이 저장소에서 통념이 뒤집힌다**(앞선 노트 그대로 유효): 셸 크기 이점(~10MB vs ~150MB)이 2GB 넘는 페이로드 앞에서 노이즈라 주 무기가 무력화되는데 Rust 학습 비용은 그대로다. 간다면 Electron.

**④ 패키징 재검토 ② — 조용한 런처 + 브라우저 앱모드 창 (사용자가 새 요구 3개를 얹으며 재론)**: 위 결론("PWA 먼저, Electron은 나중")이 나온 뒤 사용자가 실제로 테스트해보려다 세 가지를 추가로 요구했다 — **① Docker Desktop 불필요 ② 실행 시 터미널 창이 안 보일 것 ③ 브라우저 탭처럼 보이지 않을 것.** ①은 이미 해결돼 있었지만(위 portable 번들), ②·③은 그때까지 어디에도 답이 없던 새 요구다.

- **② 터미널 창 — `.command`로는 원리적으로 안 된다.** macOS는 `.command` 확장자를 **항상 Terminal.app에서 여는 것으로 고정**돼 있다(파일 자체의 설계다, 스크립트 내용과 무관). 감출 방법은 진짜 `.app`으로 감싸는 것뿐 — Xcode나 Swift 컴파일 없이 **Automator "응용 프로그램"이나 `osacompile`로 셸 스크립트를 감싸면** 된다(서버는 백그라운드로 돌리고 출력은 로그 파일로). 서명은 로컬 실행 자체엔 필요 없다 — Electron 검토 때 나온 것과 같은 지점("서명은 배포할 때만 걸리는 비용")이 여기도 그대로 적용된다.
- **③ 브라우저 탭처럼 안 보이게 — 실측으로 확인**: `open -n -a "Google Chrome" --args --app="http://127.0.0.1:8000" --user-data-dir=<격리 폴더>`를 이 기계에서 직접 실행해 확인했다. **주소창·탭·북마크바가 전혀 없는 독립 창**이 뜬다 — Electron·Tauri 없이, 서명 비용 없이 얻는다(`nativefier` 같은 도구가 실제로 쓰는 것과 같은 원리). Edge도 크로미움이라 같은 플래그가 그대로 먹는다. **한계**: Chrome이나 Edge가 설치돼 있어야 발동한다(Windows는 Edge가 기본 내장이라 문제 없음, Mac은 없으면 일반 브라우저 탭으로 폴백해야 함). Activity Monitor에는 여전히 "Google Chrome"으로 뜨고 `/Applications`에 박히는 독립 앱 아이콘은 아니다 — 그 마지막 차이를 없애려면 Electron이 필요하다.
- **사용자 결정 — 근접 무료 조합으로 확정, Electron은 계속 미룬다.** 세 요구를 만족하는 조합(portable 번들 + 조용한 `.app` 런처 + Chrome/Edge 앱모드)과 Electron(서명 비용 + 플랫폼 4종 빌드) 중 전자를 선택 — 위 "권고 — 2단계" 노트의 ①이 그대로 이어지되, ②(Electron)로 넘어갈 필요 자체가 없어졌다는 뜻. Chrome/Edge 미설치 폴백만 남는 리스크로 받아들인다.
- **다음 단위(다음 세션 착수)**: `scripts/build_bundle_macos.sh`가 만드는 `start.command`를 조용한 `.app` 런처로 교체 — ① 서버를 백그라운드로 실행(로그는 파일로) ② `/api/health` 폴링 ③ 준비되면 Chrome/Edge를 격리 프로필+앱모드로 열고, 둘 다 없으면 기본 브라우저 탭으로 폴백. 판단할 것: 격리 프로필을 어디 둘지(매번 임시 폴더 vs `~/Library/Application Support/AIsaac`에 고정 — 후자면 재실행해도 같은 브라우저 프로세스로 안 겹치는지 확인 필요), 앱 창을 닫았을 때 백엔드 프로세스를 같이 죽일지(Docker판과 달리 지금 portable 런처는 포그라운드라 창 종료와 서버 종료가 묶여야 자연스럽다).

### 9.5 연구 워크플로우 화면 — 설계 논의 전 과정 (08-03, 구현 완료)

RoadMap.md엔 최종 확정된 화면 설계(완료 체크 타임라인 + "다음으로 갈 수 있는 곳" 추천 버튼 패널, 세션은 챗과 같은 가벼운 패턴)만 남기고, **거기 도달한 논의 과정**은 여기로 옮긴다. 08-03에 착수 전 세션 내내 논의로 남긴 설계 근거이고, 실제 구현은 08-04에 그대로 따라 완료됐다(위 ✅ 완료 표 "연구 워크플로우 화면(⑥⑦ UI) — 구현 완료" 이하 여러 행 참고, 이후 체크포인트 히스토리·복원/초안 편집/브랜치형 타임라인/참고문헌 재시도/재생성 지시 반영/단계별 메모까지 계속 얹혔다).

**1. 지금 없는 것 (착수 시 제일 먼저 확인)**

- `research_workflow.py`는 그래프 빌더만 있고 **`main.py`가 이 그래프를 컴파일해서 쓰는 코드가 전혀 없다.** `main.py`의 `lifespan`은 지금 `orchestrator.graph`만 `AsyncSqliteSaver`로 컴파일한다(23~34번째 줄 근처) — 연구 워크플로우용 두 번째 체크포인터(`research_workflow.CHECKPOINT_DB_PATH`, 파일이 이미 분리돼 있음)를 똑같은 패턴으로 열어 `app.state.research_graph`에 올려야 한다. `async with`를 두 개 중첩하거나 `AsyncExitStack`을 쓰면 된다.
- `research_workflow.py` 자체의 5단계(hypothesis→design→operation→report→writing)와 `outcome` 5갈래(`analyze_results`)는 이미 완성·테스트돼 있다 — 그래프 로직은 안 건드려도 된다. 화면 작업은 **그 위에 API+프론트만 얹는 것.**

**2. 화면 설계가 이렇게 된 이유(대화로 도달한 결론, 순서대로)**

- **처음 제안(화살표 진행바 1→2→3→4→5)을 스스로 뒤집었다**: `route_by_stage`가 `state.stage` 값만 보고 라우팅하므로 **어디서든 어느 단계로나 다시 갈 수 있다.** 특히 `analyze_results`의 `outcome`이 `hypothesis_wrong`/`design_flawed`면 `operation`에서 `hypothesis`나 `design`으로 **되돌아가는 게 정상 경로**다(1→2→3→1처럼 튐). 화살표 진행바는 이 되돌아가는 흐름을 "퇴보"처럼 보이게 해서 부적절.
- **사용자 지적①**: "타임라인은 필요한데(어디까지 왔는지), 다음에 어디로 갈 수 있는지 보여주는 게 있으면 퇴화가 아니라 선택지 고르는 느낌이지 않겠냐" — 이게 최종 설계의 핵심이 됨.
- **실제로 갈림길이 있는 곳은 `operation` 하나뿐**이라는 걸 단계별로 다 짚어봄:
  - `hypothesis` 완료 → 다음 옵션은 `[설계 진행]` 하나뿐
  - `design` 완료 → `[실험 시작]`(주 경로) / `[설계 재생성]`(같은 stage 재호출)
  - **`operation` 완료 → `outcome` 값에 따라 5가지 다 유효한 선택**: `[보고서 작성]`(supported) / `[가설부터 재수립]`(hypothesis_wrong) / `[재설계]`(design_flawed) / `[같은 설계로 재실험]`(execution_error) / `[결과 다시 입력해 재분석]`(analysis_error)
  - `report` 완료 → `[논문 작성]`(주 경로) / 이전 단계로 돌아가 고치기
  - `writing` 완료 → `[초안 재생성]` (다음 단계가 아직 없어 사실상 종점)
- **사용자 지적②**: "파란색만이 아니라 이름 뒤에 `[추천]`이라고 달아서 직관적으로" — 색만으로 강조하면 안 되고, `outcome`이 가리키는 옵션 버튼 라벨 뒤에 **`[추천]` 텍스트를 붙이는 것**으로 확정. 나머지 옵션은 다 똑같이 버튼으로 노출하되 `[추천]` 표시만 없음 — "시스템은 신호만 주고 결정은 사람이" 원칙(이 프로젝트 전체에 깔린 원칙)과 일치.
- **타임라인은 "완료 체크"로 단순화**: 가설→설계→실험→재설계→실험→... 같은 실제 재방문 순서를 전부 그리려면 체크포인터 히스토리(`aget_state_history`)를 따로 조회해야 해서 1차 범위를 넘는다. 지금은 **5단계 중 값이 채워진 것만 체크 표시 + 현재 단계 강조**로 충분(단순 경로부터) — 재방문 이력까지 그리는 건 나중에 필요해지면.

**3. 놓치면 안 되는 위험 — 08-04 체크포인트 히스토리·복원으로 해소**

되돌아가서 이전 단계를 재생성하면(예: `report`까지 만든 뒤 `hypothesis`를 다시 트리거) 그 단계 값은 **덮어써지는데, 이미 만들어둔 뒤 단계 값(design/analysis/experiment_report/draft)은 자동으로 무효화되지 않고 낡은 채 그대로 남는다.** `WorkflowState`엔 버전 관리가 없다. 화면이 "재생성하면 이후 N개 단계가 낡아집니다" 같은 경고를 줄지는 논의만 하고 결론을 안 냈다가 → 08-04에 체크포인트 히스토리·복원 기능으로 근본 해결 — 자체 버전 관리 필드를 새로 만드는 대신 LangGraph 체크포인터가 이미 매 호출마다 남기는 스냅샷을 그대로 활용.

**4. 세션(연구 여러 개) 관리 — 챗과 같은 패턴으로 확정**

- 처음엔 `research_sessions` 테이블에 `stage`까지 자동 동기화하는 무거운 안을 제안했다가, 사용자 반문("그냥 AI 세션 나뉘듯이 하면 안 되나")으로 재검토 — **챗도 지금 "세션 목록" 기능이 없다**(thread_id를 세션마다 새로 발급하고 사이드바에 캡션으로만 보여줌, `chat.py` 참고). 처음엔 그 수준(목록 없이 thread_id만 기억)으로 축소하려 했으나, 사용자가 "제목만이라도 필요할 것 같다 — AI도 왼쪽에 세션 제목 뜨고 수정·닫기가 되잖아"라고 재지적해 **가벼운 세션 목록 + 제목 수정 + 닫기**로 최종 확정.
- 확정 스키마(새 모듈 `research_sessions.py`, `interests.py`/`equipment.py`와 완전히 같은 CRUD 패턴, `data/app.db` 공유):
  ```sql
  CREATE TABLE research_sessions (
      thread_id TEXT PRIMARY KEY,
      title TEXT NOT NULL,      -- 사이드바 표시용, 자유롭게 수정 가능(기본값=topic)
      topic TEXT NOT NULL,      -- 가설 생성에 실제로 쓰인 원문, 불변
      stage TEXT NOT NULL,      -- 목록에 지금 단계 표시용
      created_at TEXT NOT NULL,
      updated_at TEXT NOT NULL
  );
  ```
  - `title`과 `topic`을 분리한 이유: 챗 세션 제목처럼 자유롭게 고칠 수 있는 이름과, 실제 연구 질문(안 바뀜)을 구분해야 한다는 게 사용자 지적의 핵심.
  - **새 연구 시작** = 이 테이블에 새 행(`thread_id`는 `uuid4()`) + `research_workflow.graph`를 그 `thread_id`로 `ainvoke({"stage": "hypothesis", "topic": ...})`.
  - **"닫기"는 이 테이블에서만 삭제** — 실제 LangGraph 체크포인트(`research_workflow_checkpoints.sqlite`)는 안 지운다(내부 스키마라 직접 삭제가 까다롭고, 개인 용도라 용량 문제도 없음). 닫은 뒤에도 `thread_id`를 알면 기술적으론 이어갈 수 있지만 목록엔 안 뜬다 — 이걸로 충분하다고 사용자 확인받음.
  - **목록에 없던 것 — 라이브 검증 체크리스트에 추가할 것**: `stage`를 매 단계 전환마다 실제로 갱신하는지, 갱신을 깜빡해 목록의 stage가 실제 워크플로우 상태와 어긋나는 경우가 생기는지는 아직 코드가 없어 확인 불가.

**5. 구현 순서 제안 (다음 세션이 그대로 따라가면 됨)**

1. `research_sessions.py` — CRUD (create/list/update_title/update_stage/delete), `interests.py` 그대로 베껴서 필드만 교체
2. `main.py`:
   - `lifespan`에 두 번째 `AsyncSqliteSaver` 컨텍스트 추가, `app.state.research_graph` 컴파일
   - `GET /research/sessions` — 목록
   - `POST /research/sessions/{thread_id}/title` — 이름 수정(`{"title": str}`)
   - `DELETE /research/sessions/{thread_id}` — 닫기(테이블에서만)
   - 워크플로우 본체 호출 엔드포인트(이름 미정, 예: `POST /research/{thread_id}`) — body는 `stage` + 선택 필드(`topic`은 최초 hypothesis 호출에만, `experiment_results`는 operation 호출에만) → `equipment.py`의 `None=명시 안 함` 패턴처럼 선택 필드는 옵셔널로 받아 넘긴 것만 `ainvoke`에 실어 보냄. 첫 호출(신규 세션)일 때 `research_sessions`에 행도 같이 생성.
   - 상태만 읽는 조회 엔드포인트도 필요(페이지 새로고침 시 재실행 없이 현재 값 보기) — `orchestrator`의 `GET /interests/draft`가 `aget_state()`로 조회만 하는 패턴 참고.
3. 프론트 새 화면(`frontend/views/research.py` 등):
   - 사이드바st 형태로 `research_sessions` 목록(제목, 클릭 시 전환, 수정, 닫기) — 없으면 "새 연구 시작" 폼(주제 입력)
   - 메인 패널: 5단계 완료 체크 타임라인(현재 단계 강조) + 현재 단계 내용(코멘트·필드) + "다음으로 갈 수 있는 곳" 버튼 패널(추천 옵션에 `[추천]` 라벨)
   - `writing` 단계 렌더링 시 **`draft_paper`가 만든 본문의 `[CITE:paper_id]` 마커를 실제 서지 형식으로 바꿔 보여줘야 함** — `references` 목록(`paper_id`→`title` 매핑)으로 치환. 지금은 마커 그대로 텍스트에 박혀 있어 화면이 이걸 안 풀면 그대로 노출됨.

이 절이 당시 다음 세션이 참고할 유일한 자료였다 — 이 대화의 전체 맥락 없이 이 절만 읽고 시작해도 되게 썼다.

### 9.6 프론트 개선 백로그 11건 — 원래 요청 전문 (08-05, 전부 완료)

RoadMap.md엔 각 항목이 "완료(날짜)"로만 압축돼 있다. 여기엔 08-05에 사용자가 실사용하며 정리한 **원래 요청 전문**을 남긴다 — 무엇을 왜 요청했는지, 착수 전에 어떤 대안을 검토했는지.

1. **연구 워크플로우 옆에 `+`** — 왼쪽 네비의 "연구 워크플로우" 항목 옆에 `+`를 두고, 누르면 새 연구를 시작하는 페이지가 열리게. 지금은 새 연구를 시작하는 입구가 화면 안에 묻혀 있다. → 08-06에 `Layout.tsx`에 `+` NavLink(`/research`) 추가로 완료.
2. **메모창을 여닫을 수 있게** — 지금은 항상 펼쳐져 있다(`NoteEditor.tsx`). → 08-06에 `open` state + ▾/▸ 토글로 완료.
3. **"…에서 갈 수 있는 곳" 다이어그램을 "다음으로 갈 수 있는 곳" 자리로 옮긴다** — 지금은 브랜치 다이어그램(`BranchTimeline.tsx`)이 위에, 다음 단계 버튼 목록(`NextOptions.tsx`)이 아래에 따로 있다. 둘이 같은 것을 두 번 보여주고 있으므로 위치를 합친다. → 08-06에 4번과 함께 완료 — `BranchTimeline`의 "미래 갈래" 미리보기 칩을 통째로 제거하고, `NextOptions`가 같은 5칸 다이어그램 언어로 실제 선택 가능한 행을 그리는 쪽으로 완전히 흡수.
4. **다음 단계 선택 UI를 다이어그램 중심으로 재설계** (이 묶음에서 가장 큰 건, 3번과 한 작업) — 지금 `NextOptions.tsx`는 **갈 수 있는 모든 방향의 프롬프트 입력창과 실험 결과 텍스트박스를 전부 펼쳐놓고** 그중 하나를 버튼으로 고르게 한다. 바꿀 방향: **다이어그램에서 갈 수 있는 곳을 다르게 표시하고(추천 경로는 더 강하게 강조), 그 버튼을 눌렀을 때만 아래에 해당 입력창이 뜨게** 한다 — 프롬프트가 필요한 단계면 프롬프트 창, 재실험이면 실험 결과 입력 창, 입력이 필요 없으면 진행 버튼만. `opt.recommended` 플래그는 이미 백엔드가 주고 있어(`BranchTimeline.tsx:118`·`NextOptions.tsx:123`에서 `[추천]` 텍스트로만 쓰는 중) 강조 표시에 바로 쓸 수 있다. 착수 전 인터랙티브 목업으로 먼저 검증(사용자와 함께) — 옵션마다 `BranchTimeline`과 같은 5칸 다이어그램을 그리고 테두리로 "선택 가능"을, 추천은 더 밝은 테두리로 표시하는 방향으로 확정한 뒤 실제 코드에 반영. → 08-06 완료.
5. **QA 챗을 왼쪽 독립 화면으로 + 세션 여러 개** — 오른쪽 상시 챗 패널은 그대로 좋지만, 왼쪽 네비에도 챗봇 화면을 두고 **연구 워크플로우처럼 세션을 여러 개** 가질 수 있게. 그리고 **가장 최근 세션을 오른쪽 패널에 띄우고, 끌 수 있게**. → 08-06에 `chat_sessions.py`+`Chat.tsx`+`useChatThread` 훅으로 완료.
6. **왼쪽 네비 순서** — `홈` 카테고리 아래에 **홈 · 챗봇 · 연구 워크플로우**, 그다음 **라이브러리**, 맨 아래 **설정**. → 08-05 부분 완료, 착수 중 순서 충돌 발견: 이 항목이 요구하는 "챗봇" 네비 항목은 5번이 만드는 것인데, 확정한 착수 순서(⑩→⑥⑦⑨→③④⑪→⑤→①②)대로면 이 시점엔 아직 없다. 사용자 확인 후 **지금 가능한 부분만 먼저 반영**: `Layout.tsx`의 "메인" 그룹에 홈+연구 워크플로우를 같이 두고(챗봇 자리는 주석으로 표시해둠), "설정"을 별도 그룹으로 떼어 맨 아래로. 5번 착수 시 표시해둔 자리에 챗봇 링크만 끼워 넣으면 끝.
7. **왼쪽 패널도 여닫을 수 있게** — 오른쪽 챗 패널에 이미 있는 토글과 같은 방식으로. → 08-05에 `Layout.tsx`에 `navOpen` state 추가로 완료 — 닫히면 `<nav>` 전체가 사라지고 오른쪽 챗 패널의 `.chat-panel-toggle`과 대칭되는 위치(좌상단 고정)에 `☰` 열기 버튼만 남는다.
8. **노트 파일 관리 — 이건 신규 항목이 아니다.** 사용자 질문("노트도 논문처럼 파일 관리 되는 거지?")에 대한 답은 **"아니다"** — `knowledge_notes.py`엔 `file_path`도 `LIBRARY_DIR`도 없고 본문은 SQLite, VDB는 검색용 색인일 뿐이라 앱 안에서의 CRUD만 된다. 파일 기반 전환은 08-05에 **의도적으로 분리**한 별건이고(RoadMap 예정 표 `무기한 연기` "노트를 논문처럼 파일로 관리 — 외부 에디터(옵시디언) 연동" 참고), 그 화면 표시 문제(서식이 그대로 기호로 보임)는 `무기한 보류` "노트 — 마크다운 뷰어"로 한 번 더 나뉜다. 이 프론트 묶음에서 다룰 게 아니다.

① 수정·닫기를 제목과 같은 줄로(예전엔 아래 별도 줄) ② 텍스트 버튼 대신 연필(✎)/x(✕) 아이콘, 평소엔 투명하고 그 줄에 호버·포커스일 때만 보임(`:hover`/`:focus-within`, 키보드 접근성도 같이 챙김) ③ "수정" 클릭 시 제목 자리가 바로 입력창으로 바뀌어 Enter나 다른 곳 클릭(blur)하면 반영, Esc면 취소 — 4곳(챗봇·연구 워크플로우 × 사이드바·카드 화면) 전부 같은 상호작용을 새 공용 컴포넌트 `components/EditableSessionTitle.tsx`로 묶어 구현(네 곳에 각각 다시 짜지 않음). **Esc 취소가 미래의 스트리밍 취소 기능보다 먼저 처리돼야 한다는 사용자 지시**를 반영해 입력창의 Esc 핸들러에서 `stopPropagation()`을 호출해둠(RoadMap "스트리밍 중 인터럽트" 항목이 아직 미착수라 지금은 확인할 대상이 없지만, 나중에 생겨도 이 컴포넌트가 먼저 가로챈다). ④ 수정/닫기가 빠지며 생긴 아래 줄에 상태 표시 — **사용자 결정으로 범위 확정**: 챗봇만 대기중(마지막 메시지가 사용자=아직 답 없음, 주로 에러로 끊긴 턴에서만 실제로 나타남)/응답됨(마지막 메시지가 AI) 2가지를 색 점으로, 그 옆에 마지막 메시지 내용 앞 50자 미리보기 — 연구 워크플로우는 이미 stage 배지가 상태 역할을 하고 있어 상태 점은 안 붙이고 stage 배지 그대로 유지, 둘 다 끝에 최근 수정 시각.

**백엔드 — 스키마 변경 없이 해결**: `GET /api/chat/sessions`을 async로 바꿔 세션마다 `aget_state()`로 체크포인트를 직접 읽어 `last_message_role`/`last_message_preview`를 계산해 얹는다 — 새 컬럼을 만들어 쓰기 경로를 하나 더 늘리는 대신(체크포인트와 값이 어긋날 위험) 매번 정본에서 계산(개인용 로컬 앱 규모라 세션 목록 조회마다 체크포인트를 다시 읽어도 무리 없음). 미리보기는 같은 스냅샷에서 `content[:50]`으로 공짜로 얻음. 프론트는 `ChatSession` 타입에 두 필드 추가.

**Research.css 죽은 코드 정리**: `EditableSessionTitle`이 대체한 `.research-session-select`/`.research-session-actions*`/`.research-session-close`를 확인 후(더 이상 어디서도 안 씀) 삭제.

### 10.3 오른쪽 챗 패널 자동 열림 설정 + 스크롤바 자동 숨김 (사용자 실사용 후 추가 요청, 같은 브랜치)

① **챗봇 화면 중복 제거**: `ChatPanel.tsx`가 챗봇 화면(`/chat`, `/chat/new`, `/chat/:id`)에서는 무조건 `null` — 왼쪽에 이미 같은 세션이 떠 있어 오른쪽 패널이 중복이었다. 챗봇을 **벗어날 때** 다시 열지는 새 `useChatPanelAutoShow.ts` 훅(localStorage 키 `chatPanelAutoShow`, 기본값 `true`)이 정하고, `Settings.tsx`에 `ChatPanelAutoShowCard`(ThemeCard와 같은 스타일)로 카드를 붙여 사용자가 직접 바꿀 수 있게 했다 — 오른쪽 버튼으로 여닫는 건 이 설정과 무관하게 항상 동작(다른 화면끼리 이동할 땐 마지막으로 골라둔 열림/닫힘 유지, `wasOnChatRoute` ref로 "방금 챗봇을 나왔을 때"만 판단).

**브라우저로 실제 재현한 버그**: `useChatPanelAutoShow`가 컴포넌트마다 독립된 `useState`라 Settings에서 토글해도 이미 마운트돼 있던 `ChatPanel` 인스턴스의 값은 안 바뀌었다(localStorage `storage` 이벤트는 다른 탭에서만 발화, 같은 문서 안 다른 컴포넌트는 못 잡음) — `window.dispatchEvent(new Event('chatPanelAutoShow-change'))`로 모든 인스턴스에 변경을 알리는 방식으로 고침(값이 바뀌는 경로를 이벤트 하나로 통일 — `setAutoShow`도 직접 `setState` 안 하고 이벤트를 거쳐 자기 자신도 갱신).

② **스크롤바 자동 숨김**(사용자 요청 — "휠 굴릴 때만 보이고 평소엔 투명"): CSS엔 "스크롤 진행 중"을 잡는 표준 가상클래스가 없어(스크롤바 자체를 드래그할 때만 반응하는 `:active`류와는 다름) `useScrollbarAutoHide.ts` 신설 — `document`에 `scroll` 이벤트를 `capture:true`로 걸어(버블링 안 하므로 캡처 필수) 어떤 스크롤 가능 요소든 잡고, 스크롤된 요소에 `is-scrolling` 클래스를 붙였다 800ms 뒤 뗀다(요소별 타이머는 `WeakMap<Element, timeoutId>`로 관리 — 여러 곳을 동시에 스크롤해도 독립). 휠뿐 아니라 트랙패드·키보드·스크롤바 드래그도 전부 `scroll` 이벤트로 들어오므로 하나로 다 커버(사용자 확인 후 채택). `Layout.tsx`에서 한 번만 호출(앱 전체 셸에 적용). `index.css`는 기존 "스크롤바 테마 대응" 규칙 위에 기본값을 `scrollbar-color: transparent transparent`/`::-webkit-scrollbar-thumb { background-color: transparent }`로 바꾸고 `.is-scrolling`일 때만 토큰 색으로 전환하도록 재작성.

## 11. 논문 작성(⑦) 착수 — 갈래 분류·보고서·초안 + 인용 검증 재검토 전 과정 (08-03)

RoadMap.md 완료 표·설계 노트엔 요약만 남기고 여기에 원래 서술을 그대로 옮긴다.

**(1) `analyze_results` 갈래 분류(사용자 지적)**: `needs_redesign: bool` 하나로는 "재실험을 요청하는 이유"를 못 구분했다 — 사용자 지적: 이론 전제가 틀렸는지/설계가 가설을 제대로 못 검증하는지/실행 과정에 문제가 있었는지/결과 서술이 불충분해 판단이 어려운지는 사람이 다음에 할 일이 전부 다르다(가설부터 재수립/재설계/같은 설계로 재실행/재분석). `ExperimentAnalysis.outcome: Literal["supported","hypothesis_wrong","design_flawed","execution_error","analysis_error"]`로 교체(`needs_redesign`은 `outcome != "supported"`로 100% 파생돼 따로 안 둠), 코드가 갈래별 고정 안내(`OUTCOME_GUIDANCE`)를 `comment`에 채움(LLM이 문장을 자유롭게 안 씀 — "결정론적 안내" 원칙). **버그 발견**: `_make_reference_node`(참고문헌 노드 3종 공용 클로저)가 `comment`를 덮어쓰고 있어 `analyze_results`가 남긴 갈래별 안내가 뒤이은 참고문헌 노드에서 사라지고 있었다 — `check_equipment_precautions`와 같은 결(기존 comment 뒤에 이어붙임)로 수정, 최종 순서는 [안전 경고]→[갈래별 안내]→[참고문헌 안내].

**(2) `report` 단계 신설**: 논문 작성이 5개 산출물 필드를 따로 읽는 대신 하나의 "사실 기준선"을 읽도록 `compile_experiment_report()`(LLM 호출 0회 — 이미 완결된 문장들을 헤더 붙여 이어붙이기만 함, 재종합하면 요약 재귀 분할에서 우려한 "재종합 중 사실이 조용히 바뀌는" 위험만 새로 생김) 신설. 별도 stage로 둔 이유: 사람이 `writing`으로 넘어가기 전에 보고서를 검토할 틈을 준다(operation 체인에 자동으로 끼우면 그 틈이 사라짐).

**(3) `writing` 단계 신설 — 논문 초안**: `draft_paper()`가 `experiment_report`+`references`만 보고 `PaperDraft`(title/abstract/introduction/methods/results/discussion + citations) 구조화 출력을 뽑음. **"사용자 문서" 재정의(사용자 지적)**: 당초 자유 텍스트 입력 필드나 별도 RAG 검색을 고려했으나, 이미 각 단계가 `reference_recommender`로 쌓아둔 `references`(보유 논문 우선) 자체가 "사용자가 가진 문서"라 새 입력·새 검색 불필요 — 범위가 그만큼 단순해짐. 인용은 본문에 `[CITE:paper_id]` 마커로(참고문헌 목록을 프롬프트에 통째로 주고 그 안에서만 고르게 지시), 인용마다 `citations` 목록에 근거(왜/어느 부분 때문인지)를 남김.

**(4) 인용 검증 — 자동화를 두 번 제안했다 두 번 다 접음(사용자 재검토)**: ① 처음엔 "인용이 실제로 근거를 뒷받침하는가"를 별도 LLM 호출로 재검증하려 했으나, 그 LLM도 결국 ②a가 LLM으로 뽑아둔 요약을 보고 판단하므로 "LLM이 LLM을 검사"하는 구조라 새 근거가 안 생긴다는 지적으로 폐기 — 초안 쓴 LLM이 왜 인용했는지 `citations`에 남기고 최종 판단은 사람이 하는 걸로 축소. ② 그다음 "paper_id가 references에 실재하는가"만이라도 정규식으로 확인하는 노드를 제안했으나, `draft_paper`의 프롬프트가 애초에 `references` 목록을 통째로 주고 "그 안에서만 인용하라"고 지시하는 걸 재확인 — 이미 눈앞에 준 목록에서 고르는 지시를 다시 따랐는지 재확인하는 셈이라 불필요로 결론. `graph.py`의 `retrieve()`→`generate()`도 검색해 넘긴 문서를 실제로 인용했는지 별도 구조 검증 노드를 두지 않는 것과 같은 결 — 프롬프트로 근거를 주고 그 안에서 생성하게 유도하는 데까지가 시스템 몫, 그 다음은 사람 몫. **결과적으로 ⑦의 자체 검토·재작성 루프(README가 적어뒀던 "Evaluator-Optimizer")는 아무것도 자동화하지 않는 것으로 정리됨** — `citations`는 게이트가 아니라 순수 표시용 근거. README의 "Evaluator-Optimizer" 표현은 더 이상 정확하지 않으므로 갱신 완료.

**남는 위험**: 프롬프트 그라운딩이 100% 보장은 아니다 — LLM이 드물게 paper_id를 오타·변형해서 쓸 가능성은 이론상 남아 있다. 실제로 걸리는 사례를 만나면(🧪 라이브 검증 체크리스트에서 확인) 그때 정규식 체크를 추가한다("단순 경로부터" — 안 걸리는 문제를 미리 만들지 않는다).

## 12. 논문·노트 저장 방식 재설계 — 1차 방향과 08-05 검토 전 과정 (08-05)

RoadMap.md엔 최종 결정만 남기고 여기에 1차 방향(사용자가 먼저 정리한 8개 계획)과 코드·브라우저 제약과 대조한 08-05 검토(A~G) 원문을 그대로 옮긴다.

export/import를 착수하려다 "지금 구조엔 원본 PDF가 없다"(`POST /papers`가 파싱만 하고 파일을 버림, 논문 본문은 `chroma_db`의 재청킹된 조각으로만 존재)는 걸 발견 → "PDF를 마크다운으로 재청킹한 결과로만 논문을 보여주면 원문 그대로의 가독성·서식이 죽는다"는 사용자 지적으로 이어져, 저장 방식 자체를 다시 설계하기로 함. **핵심 전제 전환**: 08-03 지식 노트 설계 노트가 "로컬 파일 직접 읽기"를 기각한 이유는 "서버 프로세스가 도는 기계의 디스크를 읽는다는 뜻이라 배포 시 그대로 깨진다"(그때는 서버=EC2, 사용자 기계=별개)였는데, 08-04에 **싱글 유저 로컬 앱으로 확정**되면서 이 전제가 사라졌다 — Docker Compose로 패키징된 지금은 "서버 프로세스가 도는 기계"가 곧 **사용자 자신의 컴퓨터**이므로(바인드 마운트로 호스트 디렉터리를 그대로 씀), 파일 경로를 추적하는 방식이 다시 유효한 선택지가 됐다. 08-03 결정은 그 시점 전제(멀티유저/서버 배포 가능성 열어둠) 아래에서는 옳았고, 이번 재설계는 그 전제가 확정적으로 사라졌다는 새 사실에 근거한 것 — 뒤집는 게 아니라 전제가 바뀐 것.

**1차 방향 — 08-05 세션에서 사용자가 정리한 것.**

1. **파일을 앱 내부로 복제·재인코딩하지 않고, 파일 경로만 추적한다.** 지금처럼 업로드 즉시 파싱해 청크로 흩어놓는 대신, "이 파일이 여기 있다"는 참조만 카탈로그(`app.db`)에 기록.
2. **논문 카탈로그 화면에서**: PDF 뷰어로 원본을 그대로 조회, 파일 경로 표시, "파일 탐색기로 열기"(OS의 Finder/탐색기에서 그 파일 위치를 열어줌) 버튼.
3. **`library/` 디렉터리 신설**(`data/`·`chroma_db/`와 별개, 저장소/배포 루트에 나란히) — 사용자가 OS 파일관리자로 이 폴더에 직접 파일을 넣거나 정리해도 앱이 그대로 인식. 논문과 노트 둘 다 이 방식으로 관리(**노트도 지금의 SQLite 저장에서 파일 기반 추적으로 전환** — 아래 "부가 영향" 참고).
4. **업로드 UI(파일 선택 다이얼로그)가 기본적으로 이 `library/` 디렉터리를 띄운다** — 사용자가 미리 파일을 옮겨뒀다면 거기서 바로 고르기만 하면 됨.
5. **폴더 단위 tracking**도 지원 — 개별 파일뿐 아니라 폴더 하나를 통째로 추적 대상으로 등록하는 경로도 필요(그 폴더 안 파일들을 일괄 인식). 자동 감시(파일시스템 워처로 새 파일 실시간 반영)까지 할지, 수동 재스캔으로 충분할지는 다음 세션에 판단.
6. **파싱·요약·VDB 색인은 등록(트래킹) 시점이 아니라 사용자 요청 시 백그라운드 작업으로 분리한다.** 지금은 `register_paper()`가 파싱+청킹+임베딩을 등록과 동시에 동기로 다 함 — 앞으로는 "파일을 트래킹에 추가"와 "그 파일을 분석(파싱·색인)"을 별개 동작으로 나누고, 후자는 사용자가 명시적으로 요청할 때만 백그라운드로 돈다. 카탈로그 화면에 "분석됨/분석 안 됨" 상태를 표시.
7. **나중 옵션(이번엔 안 만듦, 로드맵에만 기록)**: `library/`를 기본으로 앱 외부(사용자가 쉽게 찾는 위치)에 두되, 설정에서 "앱 `data/` 안에 보관"으로 전환하는 옵션도 나중에 추가. 두 저장 위치를 오가는 마이그레이션까지는 지금 범위가 아님.
8. **export 화면에 export 범위 선택지 추가**: "파싱된 내용(+메타데이터)만" vs "원본 파일까지 포함" 중 사용자가 고르게. 파일 경로 추적 방식으로 바뀌면 "원본"이 실제로 다시 존재하니 이 선택지가 의미를 가짐(예정 표 export/import 항목이 이 재설계에 종속된 이유).

**08-05 검토 — 위 1차 방향을 코드·브라우저 제약과 대조한 결과.** 8개 항목 중 2개는 브라우저 제약상 그대로는 구현이 불가능하고, 2개는 축을 바꾸는 게 낫다는 결론. 방향 자체(전제 전환 논리, 파일 추적, 파싱 분리)는 그대로 유효하다.

- **A. 계획 1·4의 근본 문제 — 브라우저는 파일 경로를 안 준다.** 지금 업로드 경로(`main.py`의 `POST /api/papers`)는 `UploadFile`을 받아 `file.filename`만 쓴다. **웹 페이지가 받을 수 있는 건 파일 이름뿐이고 전체 경로는 원천적으로 안 온다**(브라우저 보안 — Chrome은 `input.value`에 `C:\fakepath\`라는 더미를 넣을 정도로 확고). 파일 선택 다이얼로그의 **시작 디렉터리를 웹페이지가 지정할 방법도 없다.** 그래서 계획 4("업로드 UI가 기본적으로 `library/`를 띄운다")는 브라우저에서 불가능하고, 계획 1도 업로드 다이얼로그를 입구로 쓰는 한 성립하지 않는다. **대안 — 입구를 뒤집는다: 업로드가 아니라 서버측 파일 브라우저.** 컨테이너 프로세스는 바인드 마운트된 `library/`를 그냥 읽을 수 있으니, OS 다이얼로그를 쓰지 말고 **앱이 `library/` 안을 나열해 화면에 보여주고 사용자가 목록에서 고르게** 한다(`GET /api/library/files`). 부수효과가 큰데, **이러면 "컨테이너 경로 vs 호스트 경로" 문제가 거의 사라진다** — DB에 저장하는 건 절대경로가 아니라 `library/` 루트 기준 **상대경로**뿐이고(`quantum/foo.pdf`), 호스트 절대경로는 화면 표시용으로만 조립하면 되며 사용자가 마운트 지점을 바꿔도 상대경로는 안 깨진다. 기존 업로드 버튼은 버리지 않고 **"고른 파일을 `library/`에 복사해 넣고 그 상대경로를 추적"**으로 재정의한다 — "앱 내부로 복제하지 않는다"는 원칙과 충돌하지 않는다(`library/`가 곧 사용자 폴더라 복사 대상이 앱 내부가 아니다).
- **B. 계획 2의 "파일 탐색기로 열기"는 조사 항목이 아니라 사실상 불가.** 원래 "실제로 되는지부터 조사 필요"로 적어뒀는데, **`http://` 페이지에서 `file://` 링크로 이동하는 것은 Chrome·Firefox·Safari가 전부 차단한다**(클릭해도 아무 일도 안 나고 콘솔에 "Not allowed to load local resource"만 뜬다). 우회로도 없다 — 있으면 그게 보안 구멍이다. **1단계 현실안은 "경로 텍스트 표시 + 클립보드 복사 버튼"**(사용자가 Finder에서 `Cmd+Shift+G`로 붙여넣음 — 초라해 보여도 100% 동작하고 코드가 몇 줄). 진짜 폴더 열기를 하려면 **호스트에서 도는 헬퍼**가 필요한데(컨테이너 안에서 `open`/`explorer`를 실행해봤자 컨테이너 안에서 실행된다), `start.command` 같은 호스트 스크립트 선례는 있지만 상주 헬퍼 프로세스 + 커스텀 프로토콜 핸들러 등록은 지금 범위 대비 과하다 — **"나중에"로 내린다.**
- **C. 신원은 경로가 아니라 내용 해시로 — 이러면 열린 질문 하나가 저절로 풀린다.** `normalize_paper_id()`(`paper/paper_id.py`)가 이미 `hash:sha256(file_bytes)`를 쓰고, 그 docstring이 **"파서를 바꿔도 안 변하는 값이어야 한다"**는 이유로 텍스트가 아닌 파일 바이트를 해시하기로 한 근거까지 남겨놨다. 이 결정을 그대로 연장해 **"경로는 변할 수 있는 속성, 해시가 신원"**으로 잡는다. 그러면 ① 사용자가 `library/` 안에서 파일을 옮기거나 이름을 바꿔도 재스캔이 해시로 같은 논문임을 알아보고 경로만 갱신한다(이동·rename 감지 로직을 따로 안 짜도 됨) ② 파일이 사라지면 레코드를 지우는 게 아니라 **"파일 없음" 상태**로 표시한다("조용히 자르지 말고 정직하게 실패") ③ **기존 논문 1편 처리 열린 질문이 없어진다** — 그 논문의 원본 PDF(`docs/거대 언어 모델의 멀티모달 입력 조건에 따른 선다형 물리 문항 풀이 성능 비교.pdf` — 08-05 `pdf_title` 작업에서 해시로 동일 논문임을 이미 확인)를 `library/`에 넣기만 하면 같은 바이트 → 같은 해시 → 같은 `paper_id`로 자동 재연결되므로 재등록 요구도 "레거시 청크 기반" 분기도 필요 없다. 추가 작업 하나: DOI/arXiv 논문은 `paper_id`가 해시가 아니라 `doi:`/`arxiv:`이므로 **파일↔레코드 매칭용 `content_sha256` 컬럼을 `papers`에 따로** 둬야 한다(`file_path`·`analysis_status`와 함께 — `paper_catalog.py`의 `_EXPECTED_COLUMNS` 패턴에 얹으면 됨).
- **D. 계획 3의 "노트도 같은 방식으로"는 분리한다.** 근거가 다르고 비용도 다르다 — 상세는 RoadMap 예정 표 무기한 연기 "노트를 논문처럼 파일로 관리 — 외부 에디터(옵시디언) 연동" 행 참고. 요약하면 논문 파일화의 근거("재청킹하면 원문 서식·가독성이 죽는다")가 노트엔 성립하지 않고, 노트의 진짜 동기는 외부 에디터 편집이라는 별개 목표라서, 묶어두면 논문 쪽 완료가 노트 쪽 난제(동시 편집 충돌·외부 편집 감지·재색인 트리거)에 발목잡힌다.
- **E. 계획 8의 export 범위 선택지는 축이 틀렸다.** "파싱된 내용만 vs 원본까지"가 아니라 **백업이냐 공유냐**가 실제 축이다 — 상세는 RoadMap 예정 표 export/import 행에 옮겨 적었다(3단계: `app.db`만 / +`chroma_db` / +`library/`).
- **F. 계획 5의 파일시스템 워처는 안 만든다.** `watchdog` 같은 의존성이 새로 붙는데다, **Docker Desktop(macOS/Windows)의 바인드 마운트에서는 호스트 파일 변경의 inotify 이벤트가 컨테이너로 안 오는 경우가 흔하다**(가상화 계층을 거치므로) — 새 의존성을 넣고도 정작 목표 환경에서 신뢰할 수 없다. "단순 경로부터" 원칙대로 **"다시 스캔" 버튼 + 라이브러리 화면 진입 시 스캔**으로 시작한다. 폴더 단위 tracking 자체는 유효(스캔 대상 루트가 `library/` 하나면 그게 곧 폴더 tracking이다).
- **G. 계획 6(파싱 분리)은 선례가 이미 있다 — 상태만 DB로 옮긴다.** `paper_ingest.py`의 `_spawn_background`(요약 생성용 스레드 스폰)가 이미 같은 패턴이다. 다만 지금은 진행 상태를 프로세스 메모리에 들고 있어 **재시작하면 "분석 중"이 증발한다** — 새 구조에서는 `papers.analysis_status`(`untracked`/`pending`/`analyzing`/`done`/`failed`) 컬럼으로 DB에 둔다. 그래야 카탈로그 화면의 "분석됨/안 됨" 표시가 재시작 후에도 정확하고 실패한 논문 재시도도 가능하다.
- **PDF 뷰어(원래 열린 질문) — 별거 없다.** `GET /api/papers/{id}/file`이 `library/`의 파일 바이트를 `Content-Type: application/pdf`·`Content-Disposition: inline`으로 스트리밍하고(FastAPI `FileResponse`) 프론트가 `<iframe src>`로 띄우면 브라우저 내장 뷰어가 렌더한다 — pdf.js 같은 라이브러리 불필요. 주의할 건 **경로 traversal**: 사용자가 준 상대경로를 `os.path.realpath`로 정규화한 뒤 `library/` 루트 접두사를 확인해 밖으로 못 나가게 막아야 한다.
- **부수 작업**: `library/`를 `.dockerignore`와 `docker-compose.yml` 양쪽에 추가해야 한다. `Dockerfile`이 `COPY ./ ./`로 컨텍스트 전체를 굽기 때문에 안 막으면 사용자 PDF가 이미지에 통째로 들어간다 — `chroma_db/`·`data/`를 넣은 것과 같은 이유·같은 자리.

## 13. 재생성 시 references 누적 — 결정까지의 전 과정 (08-03 발견 → 08-05 결정, 구현은 착수 전)

RoadMap.md엔 최종 결정(superseded 표시)만 남기고 여기에 문제 정의·미루기로 한 이유·후보 비교 원문을 옮긴다. **구현 자체는 아직 착수 전** — 결정만 난 상태다.

참고문헌 노드의 comment는 "참고문헌이 부족하면 재생성을 눌러주세요"라고 안내하는데, 재생성은 같은 stage로 그래프를 다시 도는 것이다. 그러면 `hypothesis` 같은 산출물 필드는 새 값으로 **덮어써지는데** `references`는 `paper_id` 기준으로 **덧붙기만** 한다 — **폐기한 가설로 찾은 논문이 목록에 그대로 남고, 중복이 아니므로 지워지지도 않는다.** 이게 문제가 되는 이유는 ⑦(논문 작성)이 이 목록을 "목록에 없는 인용은 환각 신호"라는 검증의 **기준**으로 쓰기 때문이다 — 목록이 폐기된 맥락으로 오염되면 그 검증의 기준선 자체가 흐려진다.

**지금 안 고치는 이유(08-03, 사용자 결정)**: 고치려면 "재생성"과 "그냥 다시 실행"을 구분해야 하는데, 그래프 입장에서 둘은 완전히 같은 `ainvoke`다. 구분하려면 UI가 재생성 의도를 별도 플래그로 실어 보내야 하고, 그 UI는 ⑦까지 나온 뒤에나 만든다. 어떤 UI로 재생성을 노출할지도 안 정해진 상태에서 정책부터 만드는 셈이라 순서가 거꾸로다.

**08-04 갱신**: "UI가 재생성 의도를 별도 플래그로 실어 보내야 하고, 그 UI는 ⑦까지 나온 뒤에나 만든다"고 미뤄뒀던 두 전제가 둘 다 충족됐다 — ⑦(논문 작성)은 08-03에 완료됐고, `NextOptions.tsx`의 "진행"/"재시도" 그룹 분리(목표 단계 인덱스가 현재 이하면 재시도)가 정확히 이 "재생성 의도" 플래그 역할을 한다. 문제 자체는 여전히 안 고쳐진 채 남아있었다 — 착수 여부는 여전히 사용자 결정 사항으로 남겨둠.

**착수 시 후보**: (a) 재생성 플래그가 오면 그 stage가 추가한 항목(`added_by_stage`가 같은 것)만 버리고 새로 채움 — 단, 사용자가 수동으로 넣은 참고문헌까지 지울 위험이 있어 "누가 넣었는지"를 구분하는 필드가 먼저 필요할 수 있음. (b) 버리지 않고 `superseded` 표시만 남겨 ⑦이 인용 후보에서 제외 — 이력이 보존돼 "왜 이 논문이 목록에 있었나"를 추적할 수 있지만 목록이 계속 길어짐.

**08-05 결정 — (b) `superseded` 표시로 확정.** 08-04에 결정 없이 멈춰 있었는데, **08-05 라이브 검증이 이 문제가 현실화되는 조건을 실제로 만들어줬다** — GUT 세션에서 `references`가 6편까지 늘었고 ⑦(`draft_paper`)이 그 목록을 인용 기준으로 **실제로 사용했다**(🧪 체크리스트 §C "`draft_paper` 인용 그라운딩" 참고). 더는 가상의 문제가 아니다. **(b)를 고른 이유 셋**: ① (a)는 "누가 넣었는지" 필드가 먼저 필요하다고 항목 본문 스스로 적고 있어 선행 작업이 붙는다. ② (a)는 **사용자가 수동으로 넣은 참고문헌을 지울 위험**이 있는데, 지운 데이터는 되돌릴 수 없다 — (b)는 지우지 않고 표시만 하므로 그 위험이 원천적으로 없다. ③ 저장소 원칙 **"조용히 자르지 말고 정직하게 실패"**와 방향이 같다(폐기된 맥락도 이력으로 남기고, 왜 제외됐는지 보이게). (b)의 유일한 단점인 "목록이 계속 길어짐"은 **⑦이 인용 후보에서 필터링하면 실질 영향이 없다** — 화면 표시에서 접어두면 사람이 보는 부담도 없다.

**착수 시 설계할 것**: `superseded` 플래그를 어디에 둘지(references 항목의 필드), 재생성 판정을 `NextOptions.tsx`의 "재시도" 그룹으로 받을지, ⑦ 프롬프트에서 superseded를 제외하는 지점.

## 14. 실사용 검증 중 실제 세션 삭제 사고 + 복구 (08-05, [브랜드] 색감·카피 반영 작업 중)

브라우저로 색상 토큰화를 검증하던 중 연구 세션 목록에서 버튼 좌표를 잘못 클릭해 실제 세션("대통합이론이란?", GUT 검증 논문 작성 중이던 실사용 데이터)이 `research_sessions` 테이블에서 삭제됐다.

### B. 대략치로 정해둔 숫자 — 실측 후 조정

- **`OWNED_CHUNK_DEPTH_FACTOR = 20` — 08-05, 합성 데이터로 확인**. 진짜 논문이 1편뿐이라 서로 다른 물리 주제 5편을 합성 텍스트로 만들어 벡터스토어에 직접 삽입해 실측(실험 후 전량 삭제, 원래 개수로 정확히 복원 확인). `k=max_results(5)`만 쓰면 가장 관련도 높은 논문 1편이 상위 5개를 전부 차지하지만, `k=100`으로 깊게 보면 6편 전부 등장하고 dedupe로 정확히 5편이 채택됨 — 배율이 왜 필요한지의 메커니즘은 실증됐으나 20이 최적인지는 여전히 실사용 필요.
- **`min_owned_results = 3` — 08-05, 위와 같은 합성 데이터로 확인**. 5편이 채택되자 `len(owned_results)=5 >= 3`이 성립해 외부 검색이 실제로 생략됨을 확인.
- **`MESSAGE_HISTORY_BUDGET_CHARS` — 08-05 코드 추적으로 확인, 질문 자체가 성립하지 않는다는 게 답이었다**. 물리 QA 경로(`graph.py`)엔 컨텍스트 예산 검사가 아예 없다 — `check_context_budget()`은 논문 요약 파이프라인에서만 쓰인다. 넘으면 provider SDK가 API 에러를 던지고 `invoke_with_fallback`이 그걸 "모델 장애"로 오인해 fallback하는 경로를 탄다. **이 발견을 별도 항목으로 승격해 실제로 고쳤다**(완료 표 "`invoke_with_fallback()` 예외 구분" 참고) — fallback 자체는 옳고, 잘못된 건 그 모델을 세션 내내 차단하는 쪽이었다. **교훈**: 조사 중 새로 발견한 결함은 원래 질문이 닫혀도 같이 닫히지 않는다 — 여기서 정확히 진단해놓고 완료 처리해버려 항목이 어디에도 안 남았고, 08-05 전반 검수가 다시 훑고서야 드러났다.
- **`classify_title_match()` 임계값 — 08-05 확인, 임계값이 아니라 그 앞 단계(`pdf_title` 추출)에서 실제 버그를 찾아 그 자리에서 수정까지 완료**. 진짜 논문 PDF로 등급 판정을 돌려봤더니 `pdf_title`이 PDF 메타데이터의 슬러그값(`'DBPIA-NURIMEDIA'`)으로 나왔다 — 임계값은 무죄, 입력값 추출이 틀렸던 것(수정 상세는 완료 표 "`pdf_title` 추출" 행 참고).

## 16. portable 번들 조용한 런처 — 실기 디버깅 전 과정 (08-06, `feature/portable-python-bundle` 브랜치)

### 16.1 1차 시도 — 손으로 만든 bash-as-.app, "응답하지 않습니다"

설계 노트("패키징 재검토 ②")가 제안한 대로 `Info.plist`(`CFBundleExecutable=AIsaac`)+`Contents/MacOS/AIsaac`(순수 bash 스크립트)로 `.app`을 직접 만들어 `build_bundle_macos.sh`에 넣었다. 처음엔 서버 기동·헬스체크·브라우저 오픈·창 감시까지 전부 한 프로세스에서 순서대로 돌게 짰다.

실제로 더블클릭(정확히는 `open`)해보니 **"'AIsaac' 응용 프로그램이 응답하지 않기 때문에 열 수 없습니다"**로 거부당했다. 처음엔 "프로세스가 너무 오래(서버 기동+브라우저 감시까지) 살아있어서 LaunchServices의 타임아웃에 걸리는 건가" 싶어 **①** 실제 작업을 통째로 별도 프로세스(`run.sh`)로 던지고 `AIsaac` 자신은 `nohup run.sh & disown; exit 0`으로 즉시 끝나게 재구성했다. 그런데도 같은 에러가 재현됐다 — 즉 "느려서"가 아니라 **순수 bash 실행파일이 CFBundleExecutable로 등록되는 것 자체가 문제**라는 뜻이었다. LaunchServices는 새로 띄운 GUI 앱이 살아있는지 Apple Event로 핑(ping)을 보내 확인하는데, 진짜 Cocoa 런타임(AppKit)이 없는 평범한 bash 프로세스는 그 핑에 답할 방법이 없다 — 프로세스가 1초 안에 끝나든 1시간을 살아있든 무관하게 원리적으로 안 되는 것.

### 16.2 osacompile로 교체 — Automator 없이 headless로 만드는 법

RoadMap 설계 노트가 "Automator '응용 프로그램'이나 `osacompile`로 셸 스크립트를 감싸면 된다"고 적어뒀던 두 옵션 중, Automator는 GUI 도구라 빌드 스크립트에서 못 쓰지만 **`osacompile`은 macOS 기본 내장 CLI 도구**(추가 설치 불필요)라 headless로 그대로 쓸 수 있다.

```bash
osacompile -o AIsaac.app <<'EOF'
on run
    do shell script "echo hi"
end run
EOF
```

이렇게 만든 앱의 `Info.plist`를 까보면 `CFBundleExecutable=applet`이라는 **컴파일된 바이너리**가 들어있다 — AppleScript 소스가 아니라 OSA 런타임 위에서 도는 진짜 Cocoa 실행파일이라, LaunchServices의 핑에 정상적으로 응답한다.

**구조 재설계**: `run.sh`를 `Contents/MacOS/` 밑이 아니라 번들 루트(`$BUNDLE/run.sh`, `main.py`·`runtime/`와 같은 레벨)에 평범한 파일로 두고, `AIsaac.app`의 AppleScript 본문은 `path to me`로 자기 위치를 알아내 `run.sh`를 `nohup ... & disown`으로 던지기만 한다:

```applescript
on run
    set appPosixPath to POSIX path of (path to me)
    set bundleRoot to do shell script "dirname " & quoted form of (text 1 thru -2 of appPosixPath)
    do shell script "mkdir -p " & quoted form of (bundleRoot & "/logs") & ¬
        " && nohup " & quoted form of (bundleRoot & "/run.sh") & ¬
        " >> " & quoted form of (bundleRoot & "/logs/launcher.log") & " 2>&1 & disown"
end run
```

`do shell script`는 백그라운드로 던진 명령이 즉시 반환하므로 앱 자신은 순식간에 끝나고, 실제 작업은 `run.sh`가 완전히 분리된 프로세스로 계속한다.

### 16.3 두 번째 벽 — 조용히 멈추거나 `getpath` 크래시(TCC)

osacompile로 바꾼 뒤에도 두 가지 다른 증상이 번갈아 나타났다:

1. **몇 분을 기다려도 로그 파일 하나 안 생김** — `mkdir -p logs`조차 실행이 안 된 것처럼 보임(bash 빌트인이라 정상이면 즉시 끝나야 함).
2. **`server.log`에 크래시**:
   ```
   Fatal Python error: error evaluating path
   pydantic_core... OSError: failed to make path absolute
   ```
   (사실은 `python3 -m uvicorn ...`이 아니라 `runtime/python/bin/python3`의 초기화 자체가 실패한 것 — CPython의 `getpath` 부트스트랩 단계.)

**두 증상 다 같은 원인이었다** — `log show`로 macOS 통합 로그를 직접 뒤져 확인:

```
tccd[...]: AUTHREQ_PROMPTING: msgID=..., service=kTCCServiceSystemPolicyDocumentsFolder,
    subject=Sub:{.../build/AIsaac/runtime/python/bin/python3}
kernel[...]: (Sandbox) System Policy: python3(...) deny(1) file-read-data /Users/.../build/AIsaac
```

저장소가 `~/Documents/Science_Chatbot` 밑에 있어서, `open`으로(LaunchServices를 거쳐) 실행된 새 프로세스가 그 밑 파일을 처음 건드릴 때 macOS의 "문서 폴더 접근" TCC 권한 검사가 걸린다. **직접 셸에서 실행하면 이 검사 자체를 안 거친다**(Gatekeeper·TCC의 on-demand 평가는 LaunchServices 경로에서만 발동 — 이게 "내가 셸에서 돌리면 항상 되는데 더블클릭하면 안 된다"는 흔한 macOS 현상의 정체다). 백그라운드로 완전히 분리된 프로세스(`run.sh`, 더 나아가 그 안의 `python3`)는 권한 팝업을 띄울 포그라운드 UI 컨텍스트가 없어서, 요청이 **응답 없이 대기**하거나(1번 증상) **거부**된다(2번 증상, `getpath`가 `EPERM` 같은 걸 우아하게 처리 못 하고 그대로 죽음).

**실측으로 확정**: 번들 전체(`cp -RL`, 682MB)를 `~/Documents` 밖(`/Users/jimmywon/AIsaac`)으로 복사해 똑같이 `open`으로 실행 — **12초 만에 헬스체크 200**, Chrome 앱모드 창까지 정상, 창을 닫으니 2초 안에 서버도 종료됐다. 문제는 코드가 아니라 **폴더 위치**였다.

**함의**: 이건 개발 폴더 위치만의 문제가 아니다. 실제 배포판을 받는 사용자도 흔히 다운로드 폴더에 압축을 풀고 그대로 실행하는데, **바탕화면·문서·다운로드 폴더는 전부 같은 TCC 보호 대상**이라 똑같이 걸릴 수 있다. 근본 해결(코드서명+공증)은 08-05 결정대로 지금 범위 밖이라, `README.txt`에 "이 폴더를 바탕화면·문서·다운로드 밖으로 옮긴 뒤 실행하세요"라는 경고를 추가하는 선에서 마무리했다.

**기각한 가설**: 처음엔 "macOS Gatekeeper가 새 바이너리를 처음 실행할 때 하는 온디맨드 악성코드 스캔이 느려서"라고 의심했다(실제로 간단한 `python3 -c "print(1)"` 테스트가 `open`을 거치면 1분 넘게 걸리는 걸 관찰했음). 하지만 TCC 로그를 직접 보고 나서 "느림"이 아니라 "권한 프롬프트가 응답을 못 받아 블록됨"이 진짜 원인이라는 걸 확인 — 최초 관찰(비정상적으로 느림)도 사실은 TCC 프롬프트가 결국 타임아웃/재시도되는 과정이었을 가능성이 높다.

### 16.4 창 종료 감지 — `wait`가 아니라 `osascript`로 물어보는 이유

서버 종료를 "브라우저 창이 닫혔는가"에 묶고 싶었다. 가장 직관적인 방법은 Chrome을 포그라운드로 띄우고 그 프로세스의 종료를 `wait`하는 것인데, 여기엔 함정이 있다: 이 런처는 **고정된 프로필 경로**(`~/Library/Application Support/AIsaac/chrome-profile`)를 쓰는데, 실측해보니 같은 프로필로 두 번째 Chrome 프로세스를 띄우면 **Chrome 자체의 싱글턴 락이 새 창만 기존 프로세스에 얹고 새로 띄운 프로세스는 곧장 종료**된다(`osascript -e 'tell application "Google Chrome" to count windows'`로 창 개수 1개 유지·메인 프로세스 1개 유지 확인). 즉 재실행 시나리오에서 `wait`를 쓰면, 창은 멀쩡히 열려 있는데 방금 띄운 프로세스는 즉시 죽어 `wait`가 곧장 반환 — 서버가 창이 열린 채로 조기 종료된다.

그래서 프로세스 생사 대신 **창의 존재 자체**를 `osascript`로 직접 물어본다:

```bash
osascript -e 'tell application "Google Chrome" to count (windows whose (URL of active tab contains "127.0.0.1:8000"))'
```

주의점 하나 — Chrome의 AppleScript 딕셔너리에서 **URL은 `window`가 아니라 `tab`의 속성**이다. `windows whose URL contains ...`는 "Google Chrome에 오류 발생: URL of window을(를) 가져올 수 없습니다"로 실패하고, `windows whose (URL of active tab contains ...)`가 맞는 문법이다(실측으로 확인).

### 16.5 CORS·API 키 버그 — 실기 스모크 테스트가 잡아낸 것

런처 자체가 된 뒤 실제로 챗봇에 메시지를 보내보니 두 가지가 더 걸렸다. 상세 원인·수정은 RoadMap.md 완료 표("포터블 번들 실기 테스트로 발견한 크래시 2건 수정")에 결론만 남겨뒀고, 여기엔 발견 과정만 짧게: ① 브라우저 네트워크 로그에서 `OPTIONS ... 400` + 곧이어 `GET ... 200`이 같이 찍히는 걸 보고 "진짜 CORS 프리플라이트라면 GET 자체가 안 갔을 텐데" 하는 의문에서 `curl`로 직접 OPTIONS를 흉내내 재현. ② 챗봇에 메시지를 보냈는데 답변이 완전히 빈 채로 끝나는 걸 보고 `curl -N` 스트리밍으로 SSE 원본을 그대로 받아보니 `final: true` 청크 자체가 없었다 — `server.log`의 트레이스백을 따라가 `models.py`의 클라이언트 생성이 `try` 블록 밖에 있다는 구조적 버그까지 확인했다.

### 16.6 남은 것

- **Windows(`start.bat`)·Linux 번들**: 아직 조용한 런처 동등물이 없다(이 세션은 macOS만) — 착수 조건은 여전히 CI 플랫폼 4종 매트릭스(`[배포] 배포 자동화` 항목).
- **코드서명·공증**: TCC 문제의 근본 해결책이지만 08-05 결정대로 범위 밖 — 지금은 문서 경고로만 대응.

## 17. portable 번들 "백엔드 연결 실패" — 원인 확정까지의 전 과정 (08-07)

결론과 수정은 RoadMap.md 완료 표(`portable 번들 "백엔드 연결 실패" — 프론트 절대 URL 박제 차단`)에 있다. 여기엔 **엉뚱한 데를 한참 팠던 과정**과 그 과정에서 확정한 사실들을 남긴다.

### 17.1 증상과, 처음에 세웠던 (전부 틀린) 가설

사용자 보고는 "종종 끌 때마다 백엔드와 연결이 안 된다"였고, 이전 세션에서 준 대응책이 "Command+Q로 Chrome을 완전히 끄고 다시 시도"였다. 그래서 처음 의심한 건 전부 **런처와 프로세스 생명주기** 쪽이었다:

1. 08-07에 넣은 단일 인스턴스 가드가 남긴 `logs/server.lock`이 꼬였나
2. 08-06 포트 자동 재시도가 8000이 아닌 포트를 잡아서 뭔가 어긋났나
3. 창 종료 감시 루프(`osascript`)가 오작동해 창이 살아있는데 서버를 죽였나
4. 사용자 추측대로 클로드코드가 `.claude/launch.json`으로 띄우는 개발 백엔드(8000)와 포트가 간섭하나

**넷 다 아니었다.** 다만 4번은 "간섭"이 아닌 다른 방식으로 실제 관련이 있었다(17.4).

### 17.2 로그가 준 결정적 단서 — 정상 실행과의 대조

`build/AIsaac/logs/server.log`에 실행 3회분이 남아 있었는데, 첫 실행과 뒤 두 실행의 모양이 완전히 달랐다.

| | 정상이던 실행 | 고장난 실행 2회 |
|---|---|---|
| 서빙된 JS | `index-D66iFGEd.js` | `index-CK4WRFFB.js` |
| 정적 자산 | HTML·JS·CSS·로고·favicon 전부 200 | 똑같이 전부 200 |
| API 요청 | `/api/chat/sessions`, `/api/notes` … 수십 건 | **단 한 건도 없음** |

서버는 멀쩡히 떠 있었고 정적 자산도 다 나갔는데 **API 요청만 0건**이었다. 서버가 죽어서 못 받은 게 아니라 **프론트가 이 서버로 안 쏘고 있었다**는 뜻이다. 그리고 정상/고장을 가른 건 런처가 아니라 **번들에 들어간 JS 파일이 무엇이냐**였다 — 이 대조가 수사 방향을 런처에서 프론트 빌드로 완전히 돌려놨다.

### 17.3 계측으로 런처를 명시적으로 반증

방향을 돌리기 전에, 의심하던 창 종료 감시 루프를 **실제로 계측해서** 무죄를 확인했다. `run.sh`를 복사해 폴링 한 줄에 로그를 붙였다:

```bash
count=$(osascript -e "... count (windows whose (URL of active tab contains \"127.0.0.1:$PORT\"))" 2>>logs/debug.log)
echo "[$(date +%T)] poll -> count='$count'" >> logs/debug.log
```

3초마다 12회 연속 `count=1`이 정확히 찍혔고 서버도 계속 살아있었다. 포트 자동 재시도도 8000이 막힌 상태에서 8001을 제대로 잡았다. **런처는 정상이다.** "Command+Q 하면 될 때도 있었다"는 인과가 아니라 우연이었고, 실제 변수는 그때그때 번들에 들어있던 dist였다.

여기서 얻은 방법론 하나 — 의심 가는 코드는 **추론으로 기각하지 말고 계측해서 기각**한다. 이번엔 계측이 없었으면 런처를 "고쳐서" 멀쩡한 코드를 망가뜨렸을 가능성이 컸다.

### 17.4 확정 — 브라우저 콘솔이 한 방에 알려준 것

Claude Browser 패널로 번들 URL을 직접 열자 콘솔에 답이 그대로 있었다:

```
Access to fetch at 'http://localhost:8000/api/chat/sessions'
from origin 'http://127.0.0.1:8001' has been blocked by CORS policy
```

번들 JS를 열어보니 `pi = \`http://localhost:8000\``가 박혀 있었다 — `client.ts`의 `import.meta.env.VITE_BACKEND_URL`이 빌드 시점에 인라인된 것. 사슬은 이렇게 닫힌다:

```
번들 JS:  http://localhost:8000 박제   ← .env의 개발용 값이 인라인됨
창 주소:  http://127.0.0.1:8001        ← 크로스 오리진
CORS:     allow_origins = localhost:5173  (main.py:73) → 전부 차단
```

**사용자 추측이 관련은 있었던 지점**: 클로드코드 개발 백엔드가 8000을 잡고 있으니 번들은 8001로 밀린다. 그러면 박제된 `localhost:8000`은 번들 자기 서버가 아니라 **클로드코드가 띄운 개발 서버**를 가리키게 된다. 간섭이 아니라 오배송이었다. 개발 서버가 꺼져 있으면 연결 거부로 실패할 뿐 결과는 같다.

이 버그가 특히 오래 안 잡힌 이유는 **실패가 조용하기 때문**이다. 화면(정적 자산)은 멀쩡히 뜨고, 서버 로그에는 200만 찍히고, 서버 프로세스도 살아있다. 사용자 눈에는 지표 타일이 `—`로만 보이니 "백엔드가 안 켜졌나"로 읽힌다 — 실제로는 백엔드가 완벽히 정상인데 아무도 말을 안 걸고 있었던 것.

### 17.5 왜 오염됐나 — dist가 공유 가변 산출물이라는 구조

`build_bundle_macos.sh`의 1/5 단계는 원래부터 `VITE_BACKEND_URL= npm run build`로 오버라이드를 걸고 있었고, **그 명령 자체는 정상 동작한다**(직접 돌려서 결과 JS에 `localhost:8000` 0건 확인). 문제는 다른 데 있었다:

- 1/5 단계가 dist를 만들고 → 4/5 단계가 그 dist를 복사한다. 그 사이에 2/5(uv sync)·3/5(파이썬 복사)가 있어 **수 분이 뜬다**.
- 그 사이 누군가 오버라이드 없는 맨 `npm run build`를 돌리면(또는 옛 dist가 남아 있으면) 4/5는 오염분을 그대로 복사한다.
- 파일 mtime상 `frontend-react/dist`는 10:55, 번들 복사본은 10:57이었다. **정확히 누가 10:55에 맨 빌드를 돌렸는지는 증거로 특정하지 못했다** — 스크립트 중간에 끼어든 것인지, 스크립트를 안 돌리고 dist만 복사한 것인지 구분할 방법이 없었다.

특정하지 못한 채로도 결론은 분명했다: **방어가 "빌드하는 사람이 올바른 명령을 쓰는가"에 걸려 있는 게 문제**다. 백엔드 화이트리스트에는 `import main` 스모크 테스트가 있는데 프론트 환경변수 박제에는 아무 검증이 없었다 — 같은 스크립트 안에서 한쪽만 지켜지고 있었다.

### 17.6 왜 `.env.production`인가 — Vite `loadEnv` 소스 확인

`node_modules/vite/dist/node/chunks/node.js`의 `loadEnv`(8.2.0 기준)를 직접 열어 확인했다:

- `getEnvFilesForMode`가 `.env` → `.env.local` → `.env.[mode]` → `.env.[mode].local` 순으로 파일 목록을 만들고, `Object.fromEntries(...flatMap(...))`로 합친다 → **뒤에 온 파일이 앞을 덮어쓴다.**
- 마지막에 `for (const key in process.env)`로 인라인 환경변수가 다시 한 번 덮어쓴다 → 빌드 스크립트의 오버라이드도 여전히 유효하다(둘이 충돌하지 않음).

그래서 `.env.production`에 `VITE_BACKEND_URL=` 한 줄이면 **`npm run build`는 mode가 production이라 무조건 빈 값**이 되고, `npm run dev`는 mode가 development라 이 파일을 아예 안 읽어 **로컬 5173/8000 분리 실행은 그대로**다. 양쪽 다 실제 빌드로 확인했다(production → `fetch("/api...")` 상대경로, `--mode development` → `localhost:8000` 유지).

`.gitignore`도 확인했다 — `.env`·`.env.local`은 제외되지만 `.env.production`은 걸리지 않는다(`git check-ignore`로 확인). 이게 걸렸으면 다른 클론·CI에서는 수정이 **조용히 무효**가 됐을 것이라, 파일을 새로 추가할 때 ignore 여부를 먼저 보는 습관이 실제로 값을 했다.

### 17.7 검사 패턴을 정하며 밟은 지뢰 두 개

**① 정상 빌드에도 `http://localhost`가 들어있다.** 순진하게 `grep localhost`로 검사하면 멀쩡한 번들이 매번 걸린다. 정체는 react-router가 `window.location`이 없을 때 `new URL()`의 base로 쓰는 폴백 상수다:

```js
function At(e,t,n=!1){let r=`http://localhost`; e&&(r=e.location.origin===`null`?...)}
```

포트가 없고 앞으로도 붙을 일이 없으므로, **포트를 요구하는 패턴**(`https?://(localhost|127\.0\.0\.1):[0-9]+`)이 정상/오염을 정확히 가른다. 깨끗한 dist는 통과하고, `localhost:8000`을 주입한 dist는 파일명까지 찍으며 실패하는 걸 양방향으로 확인했다.

**② zsh에서 `"$pat[0-9]*"`는 glob이 아니라 배열 첨자다.** 오탐 검사를 처음 돌렸을 때 `grep -o "$pat[0-9]*"`가 `o`를 11189건 찾아내는 이상한 결과가 나왔다. zsh는 `$pat[0-9]`를 변수 `pat`의 첨자 접근으로 해석한다(bash와 다른 지점). `"${pat}[0-9]*"`로 감싸거나 패턴을 통째로 리터럴로 쓰면 된다. **검사 스크립트가 조용히 엉뚱한 걸 검사하고 통과하는 건 검사가 없는 것보다 나쁘므로**, 이 종류의 오작동은 반드시 대조군(일부러 오염시킨 입력)으로 잡아야 한다 — 실제로 대조군이 없었으면 못 알아챘다.

### 17.8 남은 것 / 안 고친 것

- **`run.sh`의 `${count:-0}` 관용구는 잠재 위험으로 남겨뒀다.** `osascript`가 실패하면(TCC 권한 거부 등) 빈 문자열이 오고, 그게 "창 0개"와 구분 없이 서버 종료로 이어진다. 이번 조사에서 **실제로 오작동하는 건 관측하지 못했으므로**(17.3) 원인이 아니었고, 관측되지 않은 문제를 고치려고 멀쩡한 코드를 건드리지 않기로 했다. 나중에 "창은 떠 있는데 서버만 죽는" 증상이 실제로 보고되면 여기부터 본다.
- **Windows 스크립트의 검증부는 문법 검사도 못 했다** — 이 환경에 `pwsh`가 없다. 스크립트 전체가 원래 실기 미검증 상태인 것과 같은 조건이다.
