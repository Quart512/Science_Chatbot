## 1. `register_paper()` 카탈로그 연동 (08-09 마무리)

`paper/paper_ingest.py`의 `register_paper()`가 정상 등록(text_extractable) 시 `paper_catalog.mark_owned()`를 호출하도록 연결했다. 추천 검색(③)이 `upsert_recommended()`로 이미 심어둔 `recommended` 행이 있으면 `owned`로 전환하고, 없으면(추천 없이 바로 등록한 논문) 새로 만든다. `title`/`authors`/`year`는 등록 과정에서 이미 계산해둔 `bib_meta`(화이트리스트로 거른 서지정보)를 재사용 — 새로 뽑지 않는다.

**스캔본은 카탈로그도 안 건드린다** — VDB에 아무것도 저장하지 않는 것과 대칭. 카탈로그 쓰기 실패는 arxiv 자동조회(네트워크, best-effort)와 달리 삼키지 않고 그대로 전파한다 — "카탈로그에 반영됨"이 이제 이 함수 계약의 일부이기 때문이다.

**cross-id 매칭은 의도적으로 미뤘다**: 추천 시점엔 arxiv_id만 있어 `paper_id`가 `arxiv:XXXX`로 계산됐는데, 등록 시점에 사용자가 (arxiv가 안 준) DOI를 새로 넘기면 `normalize_paper_id()`가 DOI 우선이라 `paper_id`가 바뀌어 기존 `recommended` 행을 못 찾고 새 행이 생기는 경우가 있다. 라이브러리 UI가 아직 없어 이런 입력이 실제로 어떻게 들어올지 모르는 채로 매칭 로직을 미리 만들 근거가 없었다 — 실제로 걸리면 그때 doi/arxiv_id 컬럼으로 보완한다.

테스트 2개 추가(카탈로그 호출 인자 확인, 스캔본 스킵 확인) + 기존 테스트가 실제 `data/app.db`를 안 건드리게 `mark_owned`를 기본 no-op으로 스텁하는 autouse fixture 추가.

## 2. 08-11 라이브러리 표면 1차

### 2.1 순서 재검토

원래 로드맵 순서는 08-10(메인 챗 라우터) → 08-11(라이브러리 표면)이었다. 08-10을 먼저 설계하다가 막혔다 — 라우터가 라우팅할 대상 중 "문서 작성기"(⑦)는 아직 없고, "추천 조회"도 막상 보니 `paper_catalog`에 `interest_id` 연결이 없어 "이 관심사에 추천된 논문"처럼 특정해서 못 물어본다(전역 목록만 가능). 게다가 07-24 아키텍처 개편 이후 "추천 조회"는 원래 메인 챗이 아니라 **라이브러리 표면**(전용 UI 버튼)이 맡는 게 자연스럽다 — 사용자 지적으로 순서를 뒤집어 08-11을 먼저 하기로 했다.

### 2.2 프론트 스택 — Streamlit 유지

로드맵은 "표면 4개엔 Streamlit 한계, React 등 전환 검토"를 08-11과 겸행하기로 했었다. 이번엔 Streamlit을 유지하기로 결정했다 — 백엔드 엔드포인트는 스택과 무관하고, `st.navigation()`이 멀티페이지 전환에 저비용이라 지금 화면부터 만들고, React 전환이 필요해지면(화면이 더 늘거나 한계에 부딪히면) 백엔드는 그대로 두고 화면만 새로 짜면 된다.

### 2.3 멀티페이지 전환

`frontend/app.py`를 `st.navigation()`+`st.Page()`로 네비게이션만 담당하게 바꾸고, 기존 챗 화면은 `frontend/views/chat.py`로 그대로 옮겼다(기능 변경 없음). `pages/` 디렉터리 자동 인식 방식(구 Streamlit 관례) 대신 `st.navigation()`을 쓴 이유: 파일명 슬러그로 페이지 이름이 정해지는 관례보다 그룹(메인/라이브러리)·아이콘·기본 페이지를 명시적으로 통제할 수 있어서다.

### 2.4 논문 탭 (`frontend/views/papers.py`)

- **`POST /papers`(신규)**: `register_paper()`가 지금까지 `paper/paper_ingest.py`의 `__main__` 스모크 테스트로만 호출되던 걸 API로 처음 노출했다. `register_paper()`가 `pdf_path`(디스크 경로)를 받는 시그니처라, 업로드 바이트를 임시 파일에 한 번 써서 그 경로를 넘긴다(`register_paper()` 자체를 bytes 인자로 바꾸는 건 이 엔드포인트 하나만을 위한 리팩터링이라 범위 밖으로 뒀다). `fitz.FileDataError`(PyMuPDF가 유효한 PDF가 아니라고 판단할 때)는 사용자 입력 검증 경계에서 나는 에러라 500이 아니라 400으로 변환한다 — 지금까지 `register_paper()`의 유일한 호출자(CLI 스모크 테스트)는 항상 진짜 PDF를 줬으니 이 실패 모드를 신경 쓸 필요가 없었지만, API로 노출되는 순간 신뢰 못 할 입력이 된다.
- **`GET /papers`(신규)**: 카탈로그 전역 조회(`status` 쿼리 파라미터로 필터). 관심사별 필터는 `interest_paper` 조인 테이블이 없어 아직 불가.
- 등록 폼 제출 후 `title_check.status == "different_paper"`면 경고 표시, 카탈로그 목록은 고정 높이(300px) 테이블로 내부 스크롤(안 그러면 논문이 많아질수록 페이지가 계속 늘어남).

브라우저로 실제 14페이지 PDF를 등록해 확인 — 122개 청크, `status: "owned"`로 카탈로그 반영까지 실제 API 경로로 재확인됐다.

### 2.5 관심사 탭 (`frontend/views/interests.py`) — 1차

- **`GET /interests`(신규)**: 지금까지 생성(`POST`)만 API로 열려 있고 조회가 없었다.
- **`DELETE /interests/{id}`(신규)**: `interests.py`에 `delete_interest()` 추가. `interest_paper` 조인 테이블이 아직 없어 이 관심사가 추천한 카탈로그 행을 같이 지울지는 그 테이블이 생길 때 정하기로 하고, 지금은 `interests` 테이블 행 하나만 지운다.
- **수동 생성 폼**: 관심사를 만드는 원래 경로는 챗의 제안 흐름(`suggest_interest_node`가 초안을 만들면 "관심사 등록" 버튼으로 저장)이지만 그 버튼이 아직 프론트에 안 붙어 있어, 관리 UI답게 직접 만드는 경로도 같이 뒀다.
- 카드별 **수정** 폼은 기존 `POST /interests`의 `update_existing_id`를 그대로 재사용.

## 3. 관심사 탭 개선 3종 (같은 세션 내 추가 요청)

### 3.1 추천 검색 페이지네이션 — "추가 검색"

기존 "지금 검색" 버튼은 매번 `start=0`으로 같은 상위 결과만 돌려줬다. `arxiv_search()`가 `start`를 0으로 고정해뒀던 걸 열어 `paper_search.search_papers()` → `paper_recommend.recommend_for_interest()` → `POST /interests/{id}/search?start=`까지 관통시켰다. 프론트는 세션에 지금까지 받은 개수(offset)를 들고 있다가 다음 페이지 요청에 그대로 넘긴다.

### 3.2 관심사 수정 시 자동 재검색

사용자 지적: "관심사가 수정되면 수정된 내용에 따라 다시 검색해야 하는데, 기존에 검색했던 논문을 활용할 수 없을까?" — 수정이 큰 변화가 아닐 수도 있으니 기존 후보를 버리지 말자는 취지.

`paper_recommend.refresh_for_interest(interest_id, existing_candidates)`를 새로 만들었다:
1. 프론트가 세션에 쌓아둔 기존 후보(이미 한 번 스크리닝된 것)를 **수정된 관심사 기준으로 재스크리닝**해서 관련 있는 것만 남긴다(관련 없어진 건 버림).
2. 동시에 `recommend_for_interest()`로 **새 페이지 하나(`start=0`)를 정상 검색**한다(카탈로그 upsert도 그 경로가 기존과 똑같이 처리).
3. 겹치는 `paper_id`는 새 쪽에서 제거(중복 표시 방지), 합쳐서 관련도로 재정렬.

**구현상 트릭**: 프론트가 들고 있는 기존 후보 dict엔 `journal_ref` 원본이 없다(`peer_reviewed` bool로만 축약돼 전달됨). `screen_candidate()`는 `candidate.get("journal_ref")`로 `peer_reviewed`를 재계산하므로, 역산해서 `peer_reviewed=True`였으면 아무 비어있지 않은 문자열을 `journal_ref`에 채워 넣는다 — `bool(journal_ref)`가 다시 `True`로 복원되기만 하면 되고, 이건 재판정이 아니라 값을 보존하는 것뿐이다.

**재스크리닝으로 살아남은 기존 후보는 카탈로그에 재upsert하지 않는다** — 프론트가 들고 있던 후보엔 애초에 doi/arxiv_id가 없어(첫 검색 응답에도 안 실었음) 정확한 메타데이터로 넣을 수 없고, "카탈로그에 남기는 것"과 "화면에 보여주는 것"을 분리하는 `paper_recommend.py`의 기존 원칙과도 맞다.

**보류한 것**: 애초엔 "기존 것과 별개로 한 번 더 신선한 재검색"도 하자는 이야기가 있었지만, 실제로는 "재검색"이라는 별도 메커니즘을 만드는 대신 그냥 기존 검색/추가 검색 버튼을 다시 누르면 되는 걸로 정리됐다 — 관심사가 수정되면 그다음 검색 클릭이 자연히 새 기준을 반영하기 때문이다.

### 3.3 검색/추가 검색 버튼 통합

두 버튼(지금 검색 / 추가 검색)이 나란히 있는 대신, 하나의 버튼이 상태에 따라 라벨과 동작을 바꾼다 — 카드에 쌓인 결과가 없으면 "지금 검색"(`start=0`), 있으면 "추가 검색"(`start=offset`)으로. 버튼 클릭 직후 `st.rerun()`을 명시적으로 호출하는데, 이는 Streamlit이 클릭 시 이미 한 번 스크립트를 재실행한 상태라 세션 상태 갱신 후 라벨이 즉시 "추가 검색"으로 바뀌려면 한 번 더 재실행이 필요하기 때문이다(안 그러면 다음 상호작용 전까지 라벨이 낡은 채로 남는다).

### 3.4 표시 개선

- "관련 있음" O/X 컬럼을 없애고, 이미 관련도순으로 정렬돼 오는 순서를 그대로 신뢰해 순위 번호로 대체했다.
- 결과 테이블에 고정 높이(300px)를 줘서 내부 스크롤로 바꿨다(논문 탭의 카탈로그 테이블도 동일 처리).

## 4. `invoke_with_fallback` 예외 화이트리스트 갭 2건

라이브러리 UI 실사용(관심사 검색) 중 API 쿼터/크레딧 소진이 겹쳐 발견했다.

**(1) `google.genai.errors.ServerError`**: `langchain_google_genai`가 내부적으로 `google-genai` SDK로 갈아탄 뒤로, gemini 과부하(503)가 `ChatGoogleGenerativeAIError`로 안 감싸이고 그 SDK의 원본 예외 그대로 올라온다. 잡지 않으면 fallback을 못 타고 `RuntimeError`도 아니라서 호출부(`screen_candidate` 등)의 "실패한 후보만 건너뛴다" 처리도 못 받고 그대로 500까지 샜다(실제 재현). `ClientError`(4xx)/`ServerError`(5xx) 둘 다의 공통 부모(`google.genai.errors.APIError`)를 잡아 전부 fallback 대상으로 포함시켰다.

**(2) `anthropic.BadRequestError`**: anthropic 계정 크레딧 부족도 400(`BadRequestError`)으로 온다. 기존 화이트리스트의 `openai.BadRequestError`와 이름은 같지만 서로 다른 SDK의 별개 클래스라 하나를 잡는다고 다른 하나까지 잡히지 않는다 — 실제로 gemini 쿼터 소진 → claude로 fallback → claude도 크레딧 부족으로 실패하는 이중 장애를 겪으며 발견했다.

`models.py`의 예외 화이트리스트에 두 타입 다 추가하고, 회귀 테스트 2개(각각 실제 예외 인스턴스를 구성해 fallback이 정상적으로 다음 모델로 넘어가는지 확인) 추가.

## 5. Gemini 모델 교체

사용자 제보: `gemini-3.5-flash-lite`가 `gemini-2.5-flash`보다 무료 티어 일일 요청 한도가 훨씬 높다. 구글 공식 모델 문서(`ai.google.dev/gemini-api/docs/models`)와 AI Studio 요금 한도 페이지로 모델 ID(`gemini-3.5-flash-lite`, 실존 확인)와 컨텍스트 윈도우(1M 토큰급, 기존과 동급)를 확인한 뒤 `model_map["gemini"]`를 교체했다. 컨텍스트 윈도우가 동급이라 `CONTEXT_BUDGET_CHARS["gemini"]`는 안전 마진을 더 늘려 200만 자로 상향했다(기존 80만 자 — 논문 전문이 걸릴 여지를 더 줄이려는 목적, flash-lite도 1M 토큰급이라 여유 있음).

`evaluation/evaluate.py`가 별도로 `gemini-2.5-flash`를 하드코딩해 쓰는 곳(judge 등)은 재현성 목적의 독립적인 선택이라 이번 교체 범위에서 제외했다.

## 7. 실험도구 DB(⑤) · 참고문헌 추천기 · 연구 워크플로우(⑥) — 백엔드 완성

08-02~08-03 구간. 로드맵의 "실험도구 DB(⑤) + 연구 워크플로우(⑥)" 한 줄짜리 항목을 실제로 착수하면서, 계획에 적혀 있던 것과 다르게 간 판단이 여럿 나왔다. 이 절은 **그 어긋난 지점들**을 남긴다 — 무엇을 만들었는지는 RoadMap 완료 표에 있다.

### 7.1 계획을 바꾼 지점 4개

**(1) ⑤의 RDB 근거가 실제로는 안 쓰였다.** "VDB vs RDB" 설계 노트가 RDB를 고른 근거는 "측정 범위가 X 이상인 장비 있나?" 같은 **SQL 범위 조회**였다. 그런데 막상 만들 때는 스펙 세부를 전부 `detail` 자유 텍스트로 몰고, 연구 워크플로우가 장비를 찾을 땐 **목록을 통째로 프롬프트에 넣어 LLM이 읽게** 했다. 결과적으로 RDB를 고른 원래 근거는 한 번도 안 쓰인 셈인데, 그렇다고 결정이 틀렸던 건 아니다 — 같은 설계 노트의 **다른** 근거("목록이 짧으니 프롬프트에 넣으면 된다")가 대신 성립했기 때문이다. 진짜 숫자 범위 조회가 필요해지면 그때 `detail`에서 컬럼을 분리한다.

**(2) 실험 설계의 "Plan-and-Execute"를 안 썼다.** README가 이 단계의 핵심 기법으로 Plan-and-Execute(계획자가 단계를 짜고 실행자가 tool을 섞어 수행, 필요시 재계획)를 적어뒀지만 분리하지 않았다. 근거: Plan-and-Execute가 막으려는 건 "설계 없이 바로 행동"인데, **이 단계의 산출물 자체가 설계 문서라 '실행'이 따로 없다** — 행동은 다음 단계에서, 그것도 사람이 실험실에서 한다. 패턴 이름이 로드맵에 적혀 있다는 이유로 구조를 맞추는 건 거꾸로다.

**(3) 안전 가드레일에 `interrupt_before`를 안 썼다.** 이건 설계 노트가 오래 "진짜 HITL이 필요한 유이한 지점"으로 지목해온 자리였다(다른 하나인 문서 작성기는 07-31에 이미 폐기). 재검토 결론은 여기도 불필요 — **이 그래프는 물리적 행동을 하지 않고**(실험은 사람이 직접 한다) 단계 전환 자체가 이미 사람 트리거라 자연스러운 승인 지점이 있다. 막을 실행이 없는데 실행을 막는 장치를 다는 셈이었다. 그래서 **이 프로젝트에 실행을 막는 진짜 interrupt가 필요한 지점은 결국 하나도 없었다**는 게 최종 결론이다.

대신 장비에 `precautions` 필드를 두고(별도 `safety_rules.py`를 만들지 않은 건 사용자 제안 — 주의사항은 장비 자체에 속하는 정보다), 설계에 그 장비 이름이 나오면 주의사항을 `comment` 맨 앞에 붙이는 **LLM 없는 이름 매칭** 노드로 처리했다. 하는 일이 "안전한지 판단"이 아니라 "사람이 미리 등록해둔 경고를 놓치지 않게 보여주기"로 바뀐 것이다 — 판정 대신 추출/신호 원칙과 같은 결.

**(4) 단계 전환 방식을 갈아엎었다(가장 큰 것).** 아래 §7.2.

### 7.2 단계 전환 — 글루 함수에서 START 라우팅으로

처음엔 가설→참고문헌→설계→…를 전부 자동으로 잇는 단일 체인이었다. 문제는 참고문헌 노드가 "선행 연구가 있는지 확인하고 재생성할지 판단하라"는 안내를 남겨도 **그래프가 다음 단계까지 그냥 달려버려 검토할 틈이 없다**는 것이었다. 단계 사이 전환은 전부 사람이 트리거해야 한다.

1차 구현은 글루 함수였다: `aget_state`로 상태를 읽고 → 파이썬 함수를 직접 부르고 → `aupdate_state`로 쓰기. 여기에 사용자가 **"그냥 START에서 라우팅하면 안 되냐"**고 물었고, 별도 토이 그래프로 실제 동작을 확인한 뒤 그쪽으로 교체했다. `WorkflowState.stage`를 `route_by_stage()`가 보고 START에서 분기하며, 각 단계는 `[생성 노드] → [참고문헌 노드] → END`다.

확인한 것 두 가지: (a) `ainvoke({"stage": "design", ...새 입력}, config)` **한 번**이면 stage 갱신과 새 입력(예: 실험 결과)이 같은 호출 안에서 함께 반영된다 — 별도 `aupdate_state`가 필요 없다. (b) 그 노드는 체크포인트에 이미 있는 이전 단계 값을 그대로 본다.

바꾸고 나서 드러난 이점이 원래 기대보다 컸다:
- **1단계만 특별 취급하던 비일관성이 사라졌다.** 글루 방식에선 가설만 그래프로 돌고 나머지는 파이썬 함수 직접 호출이라 스트리밍·트레이싱이 단계마다 달랐다.
- **"재설계 필요" 판정에 되돌아가는 엣지가 필요 없다.** 사람이 stage를 "design"으로 되돌리기만 하면 된다.
- 단계가 늘어도 새 글루 함수 없이 라우팅 분기 + 엣지만 추가하면 된다.

### 7.3 `screen_candidate`를 관심사 dict에서 문자열로 좁히기

참고문헌 추천기는 ③ 추천 검색과 검색·스크리닝 부품을 공유해야 하는데, 입력 성격이 다르다 — ③은 "등록된 넓은 주제 하나", 추천기는 "문장 하나"마다 호출된다. `screen_candidate(candidate, interest: dict)` 그대로 쓰려면 **가짜 interest 객체를 만들어 넘겨야 했다.**

그래서 두 번째 인자를 `topic: str` 자유 텍스트로 좁히고, 관심사 4필드를 텍스트로 조립하는 책임은 호출자(`paper_recommend._interest_topic_text()`)로 밀었다. 이 함수는 이제 텍스트의 출처를 몰라도 된다. 인터페이스를 **넓히는** 대신 **좁혀서** 재사용성을 얻은 사례다 — 시스템 프롬프트도 "'찾는 것'이 적혀 있다면 거기 초점을 맞추되, 그런 구분이 없으면 이 기준은 무시하라"로 양쪽을 다 받게 고쳤다.

### 7.4 리뷰 8건 — 테스트가 원리적으로 못 잡던 것들

구현 직후(다음 기능 얹기 전) 전체를 훑어 8건을 발견·수정했다. 상세는 RoadMap 08-03 행에 있고, 여기엔 **교훈이 남는 것 세 개**만 적는다.

**(A) `CREATE TABLE IF NOT EXISTS`는 컬럼을 추가하지 않는다.** `precautions`를 나중에 스키마에 넣었는데, 이 문장은 테이블이 이미 있으면 아무것도 안 한다. 3필드 시절 테이블이 남아있는 환경(EC2는 `data/`가 바인드 마운트라 DB가 살아남는다)에 올리면 INSERT가 `no such column`으로 터진다.

**테스트가 이걸 원리적으로 못 잡는다는 게 핵심이다** — 매 테스트가 새 `:memory:` DB로 시작하니 "기존 테이블이 있는 상태"가 아예 재현되지 않는다. 로컬 `data/app.db`에도 아직 `equipment` 테이블이 없어서(스모크 테스트를 안 돌렸다) 개발 중에는 영원히 안 걸릴 버그였다. 구버전 테이블을 직접 만들어 재현하는 테스트를 추가하고, 수정을 되돌려 실제로 그 예외로 실패하는 것까지 확인했다. §README_12의 "개별 함수 단위 pytest로는 못 잡는 버그가 있다"와 같은 계열인데, 이번엔 **환경 상태**가 변수였다.

**(B) 예외 타입을 열거하면 어댑터가 바뀔 때 샌다.** 참고문헌 노드는 `RuntimeError`(모델 소진)만 잡고 있었다. 그런데 호출 경로가 `recommend_references → paper_search → arxiv_api`라 arxiv가 잠깐 죽으면 `requests.RequestException`이 그대로 올라오고, **방금 LLM으로 만든 가설·설계가 체크포인트에 커밋되지 못하고 통째로 날아간다.** 주석엔 "부가 기능 실패가 핵심 결과를 막지 않는다"고 적혀 있었지만 코드는 그렇지 않았다.

여기선 `Exception`으로 넓히는 게 맞다고 판단했다 — 이 노드의 계약이 "무슨 일이 있어도 앞 단계 산출물을 지킨다"이고, 타입을 열거하면 어댑터를 갈아끼울 때마다 목록이 새는데 **새는 방식이 하필 "핵심 결과 소실"**이기 때문이다. 대신 잡은 예외 타입을 로그에 남겨 조용히 삼키지는 않는다.

**(C) 하나의 상수가 두 가지 역할을 겸하고 있으면 한쪽을 못 바꾼다.** 보유 논문 검색이 `k=max_results(5)`였는데, 논문 한 편이 100청크를 넘으니 유사도 상위 5개는 거의 항상 같은 논문의 인접 청크다. `paper_id`로 dedupe하면 1~2편만 남아 **보유 논문이 있어도 매번 외부 검색으로 넘어갔다**(`retrieve()`가 `MAX_CHUNKS_PER_PAPER`로 푼 것과 같은 성격의 문제).

고치려고 `k`를 키우다가 알아챈 게, `k`가 우연히 **결과 개수 상한** 역할도 겸하고 있었다는 것이다. 깊이만 키웠으면 참고문헌이 20편씩 나올 뻔했다. 청크 깊이(`OWNED_CHUNK_DEPTH_FACTOR`)와 논문 수 상한(`max_results`)을 별개 축으로 분리했다. 07-28의 "라벨(표시용)과 소속 판정을 같은 값에서 파생시키지 말라"와 같은 형태의 실수다 — **하나의 값이 두 요구를 겸하고 있으면 한쪽 요구가 바뀔 때 반드시 걸린다.**

한편 깊이를 키우면 "관련 없는 보유 논문"도 들어오므로 유사도 임계값을 둘지 논의했는데, **두지 않기로 했다**(사용자 결정) — 보유 논문은 사용자가 직접 등록한 것 자체가 신뢰 신호라는 기존 원칙(`retrieve()`가 논문 VDB를 무조건 신뢰하는 것)을 유지하고, 실측 없이 정한 L2 거리 상수는 근거 없는 숫자만 하나 늘리는 셈이라서다.

### 7.5 테스트 대역이 계약을 가리고 있던 두 사례

리뷰 중 **테스트가 초록불인데 검증은 안 하고 있던** 경우를 두 개 발견했다.

첫째, `references` 항목은 `source="owned"`일 때 `reasoning` 키가 없었는데(스크리닝을 안 거치니까) 테스트 헬퍼 `_ref()`가 owned에도 `reasoning=""`를 넣고 있었다. **생산 코드가 만들지 않는 모양으로 테스트를 하고 있었던 것**이라, ⑦이 `r["reasoning"]`에서 `KeyError`를 맞을 자리가 그대로 남아 있었다. 생산자가 빈 문자열로 채우도록 통일했다 — 소비자가 source별 키 차이를 기억해야 하는 규칙은 소비자가 늘수록 언젠가 깨진다.

둘째, 참고문헌 노드의 예외 처리를 검증하는 테스트에서 대역이 `def _boom(text)`였다. 노드가 `disabled_models=`를 키워드로 넘기게 바뀌자 이 대역은 의도한 예외가 아니라 **`TypeError`를 던졌는데, 그것도 `Exception`이라 테스트는 그대로 통과했다.** 엉뚱한 이유로 초록불이 되는 상태다. `**kw`를 받도록 고쳤다.

둘 다 "테스트가 통과한다"와 "테스트가 의도한 것을 검증한다"가 다르다는 사례다.

### 7.6 서킷 브레이커를 참고문헌 경로까지

`recommend_references`는 검색어 추출 1회 + 스크리닝 N회로 **워크플로우에서 LLM을 가장 많이 부르는 지점**인데, `disabled_models`를 받지도 돌려주지도 않고 토큰도 버리고 있었다. RoadMap 08-12 항목이 "`paper_screening`은 별개 배치 파이프라인이라 서킷 브레이커 범위 밖"이라 적어둔 게 있었지만, 그건 cron/배치에서 부를 때 얘기였고 지금은 `disabled_models`를 이미 들고 다니는 그래프 안이라 전제가 다르다.

고치면서 알게 된 건, 이게 **단계 간 문제가 아니라 한 번의 호출 안에서도 낭비**였다는 점이다 — 검색어 추출에서 gemini가 죽어 claude로 fallback해도 그 사실이 버려지니, 이어지는 후보 N개가 **매번 gemini부터 다시 때려보고 실패**한다. `screen_candidate()`에 선택 인자로 추가(기본 `None`이라 ③ 배치 경로는 무영향)하고, `recommend_references()`가 `(목록, disabled_models, tokens_used)` 3튜플로 반환하게 했다.

겸사겸사 `_add_tokens`가 `graph.py`·`research_workflow.py`에 같은 코드로 있고 여기가 세 번째가 될 참이라 `models.add_tokens`로 올렸다 — 토큰은 모델 호출의 부산물이므로 "모델 정책은 `models.py` 단일 지점" 규칙에 속한다.

#### (C) 보유 논문 검색 — 왜 `doc_type` 필터가 아니라 `k` 확대인가

버린 안 세 개:

- **`doc_type`을 `summary`/`abstract`로 필터**: 논문당 문서가 1~2개라 청크 쏠림이 원천적으로 사라진다. 처음 떠올린 안이었고 곧 뒤집었다 — **요약은 lazy 생성**이라 방금 등록한 논문은 `fulltext_chunk`밖에 없다. 필터를 걸면 그 논문은 참고문헌 후보에서 통째로 빠진다. "요약이 우연히 생성돼 있는 논문만 인용될 수 있다"는, 논문 내용과 무관하고 사용자가 알 수도 없는 기준이 생긴다.
- **`MAX_CHUNKS_PER_PAPER`식 논문당 상한**: `retrieve()`가 같은 증상을 이걸로 풀었으니 대칭처럼 보이지만, 여긴 **이미 dedupe로 논문당 1개로 접고 있다**. 문제는 *출력*에서 한 논문이 자리를 먹는 게 아니라 *입력 창(k)*이 좁은 것이라 상한을 더 걸어도 아무것도 안 바뀐다. 증상이 같아도 원인이 다른 경우.
- **유사도 임계값(거리 컷)**: §7.4 마지막 문단 참고.

`k`를 키우는 비용이 거의 0이라는 점도 판단에 들어갔다 — 쿼리는 `k`와 무관하게 **한 번만** 임베딩되고 Chroma는 어차피 컬렉션 전체와 거리를 계산한다. `k`는 그중 몇 개를 실제로 꺼내올지만 정하므로, 100개를 꺼내도 로컬 메모리 복사 수준이다. 배율 20은 실측(122청크/논문) 기반 대략치다.

#### (G) 장비 이름 매칭 — 왜 정교화하지 않았나

**단어 경계(`\b`) 매칭을 버린 결정적 이유는 한국어 문법이다.** 파이썬 `re`의 `\b`는 `\w` 경계에서 성립하는데 한글 음절은 유니코드에서 `\w`다. 조사가 명사에 그대로 붙는 한국어에서는 `\b레이저\b`가 `"레이저를 사용한다"`를 **매칭하지 못한다**("를"도 단어 문자라 경계가 안 생김). 즉 정교화하려던 방식이 정상적인 한국어 문장에서 오히려 못 찾는다.

더 근본적으로, 두 방식은 **틀리는 방향이 다르고 그 둘은 대칭이 아니다**:

| 방식 | 틀릴 때 | 결과 |
|---|---|---|
| 부분 문자열 | 과검출 — "레이저"가 "레이저 거리계"에도 걸림 | 관계없는 주의사항이 하나 더 보임 |
| 단어 경계 | 미검출 — "레이저를"을 못 잡음 | **안전 경고가 안 뜸** |

안전 가드레일에서 감수할 수 있는 건 앞쪽이다. 그래서 실제로 고친 건 **빈 이름 가드 하나뿐**이다 — 파이썬에서 `"" in "아무 텍스트나"`는 `True`라, `name=""`인 행이 있으면 그 주의사항이 모든 실험 설계에 붙는다(`NOT NULL`이어도 `""`는 통과하므로 실제로 가능한 상태).

다만 과검출에도 대가는 있다: **관계없는 경고가 매번 뜨면 사람이 경고를 안 읽게 된다.** 그게 관찰되는 시점이 매칭 규칙 정교화의 착수 시점이다.

#### (F) 서킷 브레이커 — 반환 형태와 공유 함수 수정 범위

**반환 형태**는 3튜플 `(목록, disabled_models, tokens_used)`을 택했다. `invoke_with_fallback`의 4튜플과 같은 모양이라 저장소 안에서 눈에 익는다는 게 이유다. 버린 안: (a) 호출자 리스트를 제자리 수정 — `models.py`가 `disabled_models = list(...)`로 **방어적 복사**를 명시해 "호출자 원본은 안 건드린다"는 경계를 세워뒀는데 반대로 가는 셈이다. (b) dict 반환 — `screen_candidate`가 그렇게 하지만 그건 주 산출물 자체가 레코드라서다. 여긴 주 산출물이 목록이라 dict에 넣으면 모든 호출자가 어차피 꺼내야 한다.

**공유 함수(`screen_candidate`)를 건드릴지**가 진짜 판단이었다. 이 함수는 ③ 추천 검색과 공유하고, RoadMap 08-12에 "`paper_screening.py`는 별개 배치 파이프라인이라 서킷 브레이커 범위 밖"이라고 이미 적혀 있었다. 그 기록을 뒤집은 근거: **그 문장은 cron/배치에서 부를 때 얘기**였고 지금은 `disabled_models`를 이미 들고 다니는 그래프 안이라 전제가 다르다. 그래도 위험을 줄이려고 **덧붙이는 방식**(기본값 `None`인 선택 인자 + 반환 dict에 키 하나 추가)을 택했다 — `paper_recommend.py`는 이 인자를 안 넘기므로 동작이 완전히 동일하다(코드로 확인).

버린 안: **검색어 추출 호출에만 적용** — 절약이 가장 작은 곳(1회)만 고치고 정작 N회는 그대로 두는 셈이라 의미가 없다.

**알려진 한계(주석 정정)**: 스크리닝이 `RuntimeError`를 던지는 경로에서는 그 호출에서 쌓인 `disabled_models`를 못 건진다 — `invoke_with_fallback`이 재귀하며 쌓은 목록이 예외와 함께 스택에 묻히기 때문. 처음 단 주석은 "여기서 죽은 모델도 이어간다"고 적었는데 **사실이 아니어서 고쳤다.** 예외에 데이터를 실어 보내는 건 정상 경로가 아닌 곳에 데이터를 태우는 설계라 안 했고, 이 `RuntimeError`는 애초에 전 모델 소진일 때만 나오므로 남은 후보도 어차피 다 실패해 실질 손해가 없다.

#### (J) 설계 프롬프트에 `testable_prediction`

끊겨 있던 지점: `generate_hypothesis`가 `testable_prediction`을 만들고 `analyze_results`가 그걸 채점 기준으로 쓰는데, **사이에 낀 `design_experiment`가 그 값을 못 보고 있었다.** 만들어둔 값을 그냥 안 쓰던 상태다.

실질 피해가 큰 이유는 **두 단계 사이에 사람이 실험실에서 실제 실험을 한다**는 점이다. 예측을 판별하지 못하는 설계가 나오면 사람이 며칠 걸려 실험한 뒤에야 "판단하기 불충분 → 재설계"가 나온다. 낭비되는 게 LLM 호출이 아니라 사람의 실험 시간이다.

값을 human 메시지에 넣는 것에 더해 시스템 프롬프트에 "그 예측이 실제로 측정 가능하도록 설계하라"는 지침을 함께 넣었다 — 값만 던지면 참고 자료로 흘려볼 수 있고, `ExperimentDesign` 스키마에는 "이 예측을 어떻게 판별할 것인가"를 담을 필드가 없어 **제약을 걸 수 있는 자리가 지침문뿐**이었다. 스키마에 필드를 새로 추가하는 안은 버렸다 — 소비자가 없는 구조화 필드를 미리 만드는 셈이고, 판별 방법은 이미 `procedure`가 담아야 할 내용이며, 필드를 늘리면 LLM은 반드시 채우고 모르면 지어낸다(`paper_extraction.py`에서 이미 겪은 것).

**검증 한계**: 이 변경은 실제 LLM으로 안 돌려봤다. 테스트는 예측 문자열이 프롬프트에 들어갔는지만 확인한다 — 설계 품질이 실제로 좋아졌는지는 돌려봐야 안다.

### 7.8 남긴 것

- **UI 없음**: ⑤⑥ 둘 다 백엔드만이고 라이브러리 탭도 워크플로우 화면도 없다(사용자 결정). 엔드포인트가 이미 있어 UI는 순수 연결 작업이라 분리해도 안전하고, ⑦까지 화면이 더 늘어난 뒤 **한 번에** 붙이면서 그 시점에 Streamlit 유지 vs React 전환도 같이 판단한다. `research_workflow.py`는 그래서 아직 `main.py`에 안 붙어 있고, 지금 이 그래프를 컴파일해 쓰는 건 `__main__` 스모크 테스트와 pytest뿐이다.

## 8. EC2 배포 트랙 폐지 (08-05 결정)

**§4·§6과 달리 이건 코드 문제가 아니라 "결정의 전제가 하위 항목까지 안 내려간" 문제였다.** 08-05에 RoadMap 전반을 검수하다 나왔다.

### 8.1 발견

08-04에 이 프로젝트는 **싱글유저 로컬 앱**으로 확정됐다 — "다운로드해서 각자 자기 컴퓨터에서 쓰는 것". 그런데 `.github/workflows/deploy.yml`은 그 뒤로도 `main` push마다 EC2로 `scp`+`ssh` 배포를 계속 하고 있었고, **그 EC2 인스턴스가 이제 무엇을 위해 도는지가 로드맵 어디에도 적혀 있지 않았다.**

이게 그냥 죽은 설정이 아니라 **파생 비용을 만들고 있었다**는 게 핵심이다. `deploy` job이 `runs-on: ubuntu-24.04-arm`으로 고정된 유일한 이유가 EC2(Graviton, arm64)였고, `docker/build-push-action`에 `platforms:` 지정이 없어서 **러너의 네이티브 아키텍처로만 이미지가 빌드**됐다 — 즉 `quart512/science-chatbot:latest`가 **arm64 전용**으로 Docker Hub에 올라가고 있었다. 로컬 배포판을 받을 사용자 대부분(Windows PC·Intel Mac·일반 x86_64 Linux)이 이 이미지를 못 돌리거나 QEMU 에뮬레이션으로 억지로 돌려야 한다는 뜻이다.

### 8.2 결정

사용자 답이 명확했다 — **"EC2를 처음 써봐서 남긴 메모였고, 앞으로 EC2는 랜딩페이지와 다운로드 페이지만 서빙한다."** 배포 트랙 폐지 확정.

폐지의 파생 효과 셋:

1. **멀티아키텍처 항목이 단순해졌다.** EC2가 없으면 arm64 러너를 쓸 이유가 사라진다 — "EC2용 push와 배포판용 push를 겸할지 분리할지"라는 설계 문제가 통째로 없어지고, **러너를 x86_64로 되돌리고 `platforms: linux/amd64,linux/arm64`를 추가**하는 것만 남는다.
2. **라이브 검증 체크리스트 §D의 `equipment` 스키마 마이그레이션 항목이 해소됐다.** 이 항목이 §D("배포 환경에서만 드러나는 것")에 있던 이유가 "EC2의 `data/app.db`에 구 스키마가 남아있을 수 있는데 로컬에선 재현이 안 된다"였는데, 그 DB가 배포 대상에서 빠졌다. 로컬 배포판 사용자는 전부 빈 `data/`에서 시작하므로 구 스키마가 존재할 수 없다.
3. **`docs/DEPLOY.md` 정리 방향이 바뀐다.** 예정 표 `최종` "문서 정리"에 "deploy ec2랑 로컬 둘로 나누기"라고 적혀 있었으나, 나눌 두 갈래 중 하나가 사라졌으므로 **로컬 배포판 절차 하나로 다시 쓰는 것**이 맞다. EC2 쪽은 랜딩/다운로드 페이지 서빙 절차만 남는다.

`deploy.yml` 자체의 수정(scp/ssh 스텝 제거 + 러너·`platforms` 변경)은 릴리즈 게이트 착수 시점에 한다 — Docker Hub 빌드·push는 배포판 이미지용으로 **그대로 필요하므로 워크플로우를 통째로 지우지는 않는다.**

### 8.3 이번 검수가 남긴 규칙

08-05에 이미 한 번 "예정 표 검수"를 돌려 **"큰 이관 작업(React 전환) 뒤에는 백로그도 같이 훑어야 한다"**는 교훈을 적어놨었다. 그런데 정작 **더 큰 전환인 08-04 싱글유저 확정에는 그 검수를 안 돌렸다** — 그래서 EC2 트랙뿐 아니라 "로깅 → 그걸로 모델 튜닝"(배포판 사용자의 로그는 저자가 모을 방법이 없다), `t4g.micro` 제약의 근거(실행 기계가 사용자 노트북으로 바뀜) 같은 것들이 옛 전제 위에 그대로 떠 있었다.

**규칙: 전제를 바꾸는 결정을 내렸으면, 그 전제 위에 쓰인 항목을 그날 전부 훑는다.** 교훈을 적어두는 것과 실제로 적용하는 것은 별개라는 게 이번에 확인된 부분이다.
